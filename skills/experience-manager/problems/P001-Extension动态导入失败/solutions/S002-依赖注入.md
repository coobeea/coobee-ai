## 一、具体实现

### 步骤 1：在 ExtensionApi 添加方法定义

```typescript
// src/main/common/extension/types.ts
export interface ExtensionApi {
  // ... 其他方法

  /**
   * 获取 ChannelRuntime 实例（避免 Extension 动态导入导致 jiti 加载失败）
   */
  getChannelRuntime(): Promise<import('../../channels/ChannelRuntime').ChannelRuntime>;

  /**
   * 获取 DiscussionStore 实例（避免 Extension 动态导入导致模块重复）
   */
  getDiscussionStore(): Promise<import('../../ai/discussion/DiscussionStore').DiscussionStore>;
}
```

### 步骤 2：在 ExtensionApi 实现方法

```typescript
// src/main/common/extension/ExtensionApi.ts
export function createExtensionApi(
  extensionId: string,
  registry: ExtensionRegistry,
  eventBusRef?: unknown
): ExtensionApi {
  return {
    // ... 其他方法

    async getChannelRuntime() {
      const { ChannelRuntime } = await import('../../channels/ChannelRuntime');
      return ChannelRuntime.getInstance();
    },
    async getDiscussionStore() {
      const { DiscussionStore } = await import('../../ai/discussion/DiscussionStore');
      return DiscussionStore.getInstance();
    }
  };
}
```

## 二、推导过程（为什么）

### 问题根因

Extension 方法中的 `await import()` 保留 jiti 上下文，导致嵌套 jiti 调用时 `app` 对象为 `undefined`。

### 解决原理

**依赖注入将动态导入移到主进程上下文中**：

```
┌─────────────────────────────────────────────────────────────────┐
│ 1. Extension (jiti) 调用 api.getChannelRuntime()               │
└─────────────────────────────────────────────────────────────────┘
                                ↓
┌─────────────────────────────────────────────────────────────────┐
│ 2. ExtensionApi (主进程) 执行动态导入 ← 脱离 jiti 上下文      │
│    → await import('../../channels/ChannelRuntime')             │
└─────────────────────────────────────────────────────────────────┘
                                ↓
┌─────────────────────────────────────────────────────────────────┐
│ 3. ChannelRuntime 顶层调用 logger ← ✅ app 对象可用           │
└─────────────────────────────────────────────────────────────────┘
```

关键点：**ExtensionApi 的方法在主进程代码中定义**（`src/main/common/extension/ExtensionApi.ts`），所以它执行的动态导入在主进程上下文中，`app` 对象是可用的。

### 权衡取舍

**优点**：

- ✅ 完全解耦（Extension 不直接依赖 `src/main/` 模块）
- ✅ 支持按需加载（只在使用时才导入）
- ✅ 符合依赖注入模式（便于测试和 mock）
- ✅ 支持单例模式（通过 `getInstance()`）

**缺点**：

- ⚠️ 需要修改 ExtensionApi（增加维护成本）
- ⚠️ 每个新依赖都要添加新方法
- ⚠️ 类型定义略复杂（需要 `import()` 类型）

**适用范围**：

- ✅ 复杂单例对象（ChannelRuntime, DiscussionStore, AgentStore）
- ✅ 需要解耦测试的场景
- ✅ 多个 Extension 共享的依赖
- ❌ 简单工具类（用 S001 更简单）

## 四、最佳实践

### 何时使用依赖注入？

1. ✅ 对象是单例（如 Store, Manager, Coordinator）
2. ✅ 需要在多个 Extension 中共享
3. ✅ 对象初始化复杂或有副作用
4. ✅ 需要便于 mock 测试

### 何时不用？

1. ❌ 简单工具类 → 用 S001 静态导入
2. ❌ 只需要路径 → 用 S003 路径缓存
3. ❌ 事件驱动场景 → 用 S004 EventBus

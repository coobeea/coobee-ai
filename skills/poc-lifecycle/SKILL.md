# POC 生命周期管理 Skill

## 概述

指导 Agent 按照标准化的 POC（Proof of Concept）生命周期流程执行复杂任务。该流程包含 5 个核心阶段：需求分析、方案设计、反思优化、实施跟踪、验收报告，确保任务执行质量、过程可追溯、结果可复盘。

## 适用场景

**何时使用此 Skill：**

- ✅ 用户要求"按照标准流程执行"、"完整地实现"、"不要偷懒"
- ✅ 任务描述包含"重构"、"架构"、"设计"、"迁移"、"改造"等复杂关键词
- ✅ 任务涉及多个文件（> 3 个）或多个模块
- ✅ 任务价值高（用户明确要求高质量交付）
- ✅ 用户明确提到需要"需求分析"、"方案设计"、"TODO 列表"等

**何时不使用此 Skill：**

- ❌ 简单任务（单文件修改、文档更新、Bug 修复）
- ❌ 紧急任务（用户明确要求"快速完成"）
- ❌ 探索性任务（用户只是"试试看"）

---

## POC 生命周期流程

### 总览

```
阶段一：需求分析 → 01-需求分析.md
  ↓
阶段二：方案设计 → 02-方案设计.md
  ↓
阶段三：反思优化 → 03-反思优化.md
  ↓
阶段四：实施跟踪 → 04-TODO.md + 05-PROGRESS.md + 06-BUGS.md
  ↓
阶段五：验收报告 → 07-验收报告.md + 08-综合报告.md
```

## 执行步骤

### 步骤 0: 创建 POC 目录

在项目根目录创建 `pocs/{project-name}/` 目录用于存放所有生命周期文档。

```bash
mkdir -p pocs/{project-name}
cd pocs/{project-name}
```

**目录命名规范**：

- 使用短横线分隔的小写英文（如 `tavern-task-lifecycle`）
- 避免空格和特殊字符

---

### 阶段一：需求分析 📋

**目标**：理解任务需求，评估技术可行性，识别约束条件

**输出文件**：`pocs/{project-name}/01-需求分析.md`

**必需章节**：

1. **需求背景**
   - 为什么要做这件事？
   - 当前存在什么问题或痛点？

2. **核心目标**
   - 期望达成的目标（3-5 个，SMART 原则）
   - 成功标准是什么？

3. **技术评估**
   - 现有技术栈能否支持？
   - 是否需要引入新技术？
   - 技术风险有哪些？

4. **约束条件**
   - 时间约束（是否有 DDL）
   - 技术约束（必须使用特定技术栈？）
   - 资源约束（预算、人力）
   - 兼容性约束（向后兼容？）

5. **涉及范围**
   - 涉及的模块、文件、接口
   - 不涉及的范围（明确边界）

6. **功能需求**
   - 核心功能列表（优先级 P0/P1/P2/P3）

7. **非功能需求**
   - 性能、安全、可维护性、扩展性

8. **风险评估**
   - 技术风险、业务风险、时间风险
   - 风险等级（高/中/低）+ 缓解措施

9. **依赖项**
   - 外部系统依赖
   - 第三方库依赖

10. **交付清单**
    - 代码文件、测试文件、文档

**模板参考**：参见 `src/main/ai/tavern/lifecycle/templates.ts` 中的 `01-需求分析.md` 模板

**验收标准**：

- ✅ 所有必需章节填写完整（无 `[请描述...]` 占位符）
- ✅ 核心目标清晰、可量化
- ✅ 风险识别不少于 3 个
- ✅ 文档长度 > 300 行

---

### 阶段二：方案设计 🎯

**目标**：设计上中下三策方案，进行对比分析，选定最优方案

**输出文件**：`pocs/{project-name}/02-方案设计.md`

**必需章节**：

1. **上策：最优方案**
   - 核心思路（架构最优、长远收益最高）
   - 技术方案（详细实现路径）
   - 改动范围（涉及的文件、模块、接口）
   - 优势（3-5 个）
   - 劣势（2-3 个，诚实面对）
   - 工作量估算（时间、代码行数）

2. **中策：平衡方案**
   - 核心思路（平衡成本和质量）
   - 技术方案
   - 改动范围
   - 优势
   - 劣势
   - 工作量估算

3. **下策：最小方案**
   - 核心思路（MVP，快速验证）
   - 技术方案
   - 改动范围
   - 优势
   - 劣势
   - 工作量估算

4. **方案对比**
   - 对比维度：开发成本、执行性能、质量保障、可维护性、用户体验、风险、扩展性
   - 对比矩阵（表格形式）

5. **选定方案**
   - 选择哪个方案？为什么？
   - 是否需要组合多个方案的优点？

**验收标准**：

- ✅ 三个方案都有完整描述（核心思路、技术方案、优劣势）
- ✅ 对比矩阵至少包含 5 个维度
- ✅ 选定方案有清晰的理由（2-3 段）
- ✅ 文档长度 > 400 行

---

### 阶段三：反思优化 💡

**目标**：对选定方案进行批判性审视，识别边界情况和风险，提出优化措施

**输出文件**：`pocs/{project-name}/03-反思优化.md`

**必需章节**：

1. **方案回顾**
   - 回顾选定的方案（1-2 段）

2. **边界情况检查**
   - 识别 5-10 个边界情况（如崩溃、异常输入、并发冲突）
   - 每个边界情况包含：
     - 场景描述
     - 当前方案是否考虑？
     - 问题分析
     - 优化方案（代码示例）
     - 优化结果

3. **安全评估**
   - 数据安全、代码安全、权限控制
   - 每个风险包含：风险描述、风险等级、缓解措施

4. **影响分析**
   - 对后端的影响
   - 对前端的影响
   - 对现有功能的影响
   - 性能影响

5. **优化调整**
   - 基于反思的优化方案（3-5 个）
   - 每个优化包含：原方案、调整后、实施优先级、理由

6. **最终方案**
   - 核心特性列表
   - 技术栈
   - 代码量统计
   - 实施优先级

**验收标准**：

- ✅ 识别至少 5 个边界情况
- ✅ 识别至少 2 个安全风险
- ✅ 提出至少 3 个优化调整
- ✅ 最终方案有清晰的改动清单
- ✅ 文档长度 > 500 行

---

### 阶段四：实施跟踪 ⚙️

**目标**：生成待办事项列表，逐项执行，记录进度和问题

**输出文件**：

- `pocs/{project-name}/04-TODO.md`（待办事项）
- `pocs/{project-name}/05-PROGRESS.md`（执行进度）
- `pocs/{project-name}/06-BUGS.md`（问题记录）

#### 04-TODO.md

**必需内容**：

1. **待办事项列表**（每个 TODO 包含）：
   - 任务名称
   - 具体描述（做什么？涉及哪些文件？）
   - 文件路径
   - 预计代码量
   - **验收标准**（至少 3 个可量化、可验证的条件）
   - 实施优先级（P0/P1/P2/P3）
   - 当前状态（[ ] 待处理 / [x] 已完成 / [-] 已取消）

2. **Sprint 划分**（建议）：
   - Sprint 1：核心功能（P0）
   - Sprint 2：集成测试（P0）
   - Sprint 3：前端界面（P1）
   - Sprint 4：验证收尾（P1）

3. **总体工作量**（表格）：
   - 各 Sprint 预计时间、TODO 数量

4. **验收标准汇总**：
   - 自动化验收（单元测试、类型检查、Lint 检查）
   - 手动验收（端到端测试、UI 验证）
   - 质量验收（代码规范、文档完整性、性能）

**示例 TODO 格式**：

```markdown
### 1. 实现 LifecycleOrchestrator

- **描述**：实现任务生命周期编排器，负责五阶段调度
- **文件**：`src/main/ai/tavern/lifecycle/LifecycleOrchestrator.ts`（新增）
- **预计代码量**：约 350 行
- **验收标准**：
  - [ ] `execute()` 方法能创建 lifecycle 目录
  - [ ] `execute()` 方法能生成 8 个模板文件
  - [ ] `execute()` 方法能根据任务复杂度选择模式
  - [ ] `execute()` 方法能提交任务到 AgentExecutor
  - [ ] `recover()` 方法能检测已完成阶段
  - [ ] `recover()` 方法能构造恢复 Prompt
  - [ ] 单元测试覆盖所有方法
  - [ ] 测试代码路径：`src/main/ai/tavern/lifecycle/__tests__/LifecycleOrchestrator.test.ts`
- **优先级**：P0（核心功能）
- **状态**：[x] 已完成
```

#### 05-PROGRESS.md

**记录格式**：

```markdown
### 2026-04-01 12:00

- ✅ 完成了 [TODO-1]
- 修改了文件：`src/main/xxx.ts`
- 新增代码：150 行
- 验收结果：✅ 通过（测试路径：xxx.test.ts）
- 备注：[补充说明]

---

### 2026-04-01 12:15

- ⚠️ 遇到了问题：[问题描述]
- 记录到：`06-BUGS.md` (BUG-001)
- 严重程度：阻塞
- 是否阻塞：是

---

## 当前状态

| 指标        | 值       |
| ----------- | -------- |
| 已完成 TODO | 5/20     |
| 完成度      | 25%      |
| 当前 Sprint | Sprint 1 |
```

#### 06-BUGS.md

**记录格式**：

```markdown
### BUG-001: [问题简述]

- **发现时间**：2026-04-01 12:15
- **严重程度**：阻塞 / 严重 / 一般 / 轻微
- **涉及模块**：[模块名]
- **现象描述**：[详细描述]
- **错误日志**：
```

[错误信息]

```
- **分析**：[根因分析]
- **修复方案**：[如何修复]
- **修复时间**：2026-04-01 12:30
- **验证方式**：[如何验证已修复]
- **状态**：[x] 已修复
```

**验收标准**：

- ✅ 所有 TODO 项都有验收标准（至少 3 个）
- ✅ 进度文件实时更新（每完成一个 TODO 记录一次）
- ✅ 遇到的 Bug 都记录在 06-BUGS.md

---

### 阶段五：验收报告 ✅

**目标**：逐项验收 TODO，生成综合报告

**输出文件**：

- `pocs/{project-name}/07-验收报告.md`（逐项验收）
- `pocs/{project-name}/08-综合报告.md`（综合总结）

#### 07-验收报告.md

**必需章节**：

1. **验收概览**
   - 验收时间、验收人、项目周期

2. **功能验收**
   - 逐项验收 TODO（按 TODO 顺序）
   - 每个 TODO 包含：
     - 验收项名称
     - 验收标准（来自 04-TODO.md）
     - 验收结果（✅ 通过 / ❌ 失败 / 🔄 部分通过）
     - 测试证据（测试代码路径、截图、日志）
     - 备注

3. **质量验收**
   - 代码规范性（ESLint、TypeScript）
   - 测试覆盖率（Vitest 报告）
   - 文档完整性（POC 文档、代码注释）
   - 性能表现（执行时间、内存占用）

4. **验收决定**
   - [ ] ✅ 验收通过 - 任务可交付
   - [ ] ❌ 验收失败 - 需要修复问题列表
   - [ ] 🔄 部分通过 - 核心功能完成，部分优化项待后续迭代

#### 08-综合报告.md

**必需章节**：

1. **执行摘要**
   - 项目背景、核心目标、实施成果（3-5 段）

2. **技术方案总结**
   - 架构选择（为什么选这个方案？）
   - 核心模块说明

3. **核心功能实现**
   - 每个核心模块的职责、关键特性、代码量
   - 代码示例（关键代码片段）

4. **测试与验证**
   - 测试覆盖情况（表格）
   - 验收标准完成情况

5. **技术亮点**
   - 3-5 个技术亮点（含代码示例）

6. **交付清单**
   - 代码文件清单（后端、前端、测试）
   - 文档清单

7. **成果展示**
   - 代码统计（文件数、行数）
   - Git 提交记录

8. **性能与成本**
   - 执行时间对比、Token 消耗对比、磁盘占用

9. **风险与缓解**
   - 风险清单（等级、缓解措施、剩余风险、实际情况）

10. **经验教训**
    - 成功之处（5 个）
    - 改进空间（5 个）
    - 意外收获（3 个）

11. **后续优化计划**
    - 短期优化（1-2 周）
    - 中期优化（1 个月）
    - 长期优化（3 个月）

12. **项目总结**
    - 核心价值
    - 适用场景
    - 最终评分（功能、代码、文档、体验、性能、扩展性）

**验收标准**：

- ✅ 所有必需章节填写完整
- ✅ 代码统计准确（通过 `cloc` 或手动统计）
- ✅ 至少 3 个技术亮点（含代码示例）
- ✅ 经验教训不少于 10 条
- ✅ 后续优化计划不少于 5 个
- ✅ 文档长度 > 500 行

## 模板变量

所有模板文档支持以下变量替换（使用 `{{变量名}}` 格式）：

- `{{taskId}}`：任务 ID
- `{{taskTitle}}`：任务标题
- `{{taskDescription}}`：任务描述
- `{{sessionId}}`：会话 ID
- `{{date}}`：当前日期（格式：2026-04-01）
- `{{timestamp}}`：当前时间戳（格式：2026-04-01 12:00:00）

**示例**：

```markdown
# {{taskTitle}} - 需求分析

> 创建时间：{{date}}  
> 任务 ID：{{taskId}}  
> 会话 ID：{{sessionId}}
```

## 执行规则

### 规则 1: 按顺序完成五个阶段

- ✅ 阶段一 → 阶段二 → 阶段三 → 阶段四 → 阶段五
- ❌ 不允许跳过阶段（除非使用快速模式）
- ⚠️ 如果某个阶段卡住，记录到 `06-BUGS.md` 并寻求帮助

---

### 规则 2: 每个阶段完成后发送通知

使用 `emit_event` 工具发送阶段完成通知（如果在 coobee-ai 环境中）：

```typescript
{
  "_event": "notify",
  "message": "任务「{{taskTitle}}」完成需求分析阶段",
  "level": "success"
}
```

---

### 规则 3: 所有文档使用 Markdown 格式

- ✅ 文件后缀：`.md`
- ✅ 使用标准 Markdown 语法（标题、列表、表格、代码块）
- ✅ 文件命名：`01-需求分析.md`、`02-方案设计.md` 等（序号 + 中文名）

---

### 规则 4: 文档质量要求

- ✅ 无占位符（如 `[请描述...]`、`[待填写]`）
- ✅ 内容充实（每个章节至少 2-3 段）
- ✅ 格式规范（标题层级正确、表格对齐）
- ✅ 无敏感信息（不包含 API Key、密码等）

---

### 规则 5: 验收标准必须可量化

**好的验收标准**：

- ✅ "单元测试覆盖率 > 85%"
- ✅ "TypeScript 类型检查通过"
- ✅ "文档长度 > 300 行"
- ✅ "包含 3 个技术亮点"

**不好的验收标准**：

- ❌ "代码质量好"（无法量化）
- ❌ "功能完整"（模糊不清）
- ❌ "用户满意"（主观判断）

## 快速模式（简化流程）

对于简单任务，可使用快速模式（三阶段流程）：

```
阶段一：需求分析（简化）→ 01-需求分析.md（只填充"核心目标"和"涉及范围"）
  ↓
阶段二：实施 → 04-TODO.md + 05-PROGRESS.md
  ↓
阶段三：验收 → 08-综合报告.md
```

**快速模式触发条件**：

- 任务描述 < 200 字符
- 涉及文件 ≤ 3 个
- 无复杂关键词（重构、架构、迁移等）
- 金额 ≤ 100

## 与 coobee-ai 系统集成

### 自动化集成

如果在 coobee-ai 系统中执行酒馆任务，系统会自动：

1. **创建 lifecycle 目录**：在任务的 workspace 下创建 `lifecycle/` 目录
2. **生成模板文件**：自动生成 8 个 Markdown 模板
3. **监控任务进度**：通过 `LifecycleMonitor` 自动监控文档生成和阶段变化
4. **推送前端更新**：通过 WebSocket 推送进度到前端
5. **任务恢复**：应用重启后自动检测并恢复挂起任务

### 手动使用

即使不在 coobee-ai 系统中，也可以手动遵循此流程：

1. 创建 `pocs/{project-name}/` 目录
2. 按照上述 5 个阶段依次创建文档
3. 每个阶段完成后，用 `git commit` 记录进度
4. 最终生成 `08-综合报告.md`

## 常见问题

### Q1: 所有任务都必须走五阶段吗？

**A**: 不是。简单任务可以使用快速模式（三阶段）。复杂度判断逻辑：

- 描述 > 200 字符
- 文件 > 3 个
- 包含复杂关键词（重构、架构等）
- 金额 > 100

### Q2: 如果 Agent 不遵守五阶段怎么办？

**A**: 在 Prompt 中强调规则，并通过 `LifecycleMonitor` 监控。如果 Agent 偏离流程，监控器会发送告警。

### Q3: 文档质量如何保证？

**A**: 通过 `DocumentValidator` 进行验证：

- 检查必需章节是否完整
- 计算质量评分（0-100 分）
- 低于 60 分自动生成修订提示

### Q4: 任务执行中应用崩溃怎么办？

**A**: 系统启动时会自动检测挂起任务（`in-progress` 且 30 分钟无更新），检测已完成的阶段，构造恢复 Prompt，重新提交。

### Q5: 用户长时间不补充资料怎么办？

**A**: 进入 `awaiting-input` 状态后：

- 12 小时发送提醒通知
- 24 小时自动取消任务

## 总结

**poc-lifecycle Skill** 提供了一套**标准化、可复用、高质量**的 POC 开发流程，适用于复杂任务的系统化管理。

**核心价值**：

- 📋 **标准化流程**：五阶段工作法，确保任务执行质量
- 📊 **过程可追溯**：所有文档留存，便于复盘和改进
- ✅ **质量保证**：验收标准 + 测试覆盖，确保交付质量
- 🔄 **可复用**：模板系统 + Skill 封装，其他项目可直接复用
- 🛡️ **风险可控**：边界情况分析 + 风险评估，降低失败概率

**适用场景**：

- 复杂任务（重构、架构、迁移、设计）
- 高价值任务（需要高质量交付）
- 需要复盘的任务（用于团队学习）

**不适用场景**：

- 简单任务（单文件修改、Bug 修复）
- 紧急任务（需要快速交付）

# 维度架构师（Dimension Architect）

## 核心职责

将**模糊需求**转化为**可量化、可评估、可落地**的维度体系。

## 核心流程（5层流水线）

```
用户需求 → ① 意图分析 → ② 目标拆解 → ③ 维度设计 → ④ 评估体系 → ⑤ 数据落地
```

### Phase 1: 意图分析

从用户原始需求中提取：

| 要素       | 说明                   | 输出           |
| ---------- | ---------------------- | -------------- |
| 原始需求   | 用户的原话             | 原文记录       |
| 真实意图   | 用户说的 vs 真正想要的 | 1-2 句精炼描述 |
| 所属领域   | 行业/学科/专业方向     | 领域标签       |
| 约束条件   | 时间、资源、能力边界   | 约束清单       |
| 利益相关方 | 谁关心结果             | 角色列表       |

**关键原则**：不急于给方案，先确认意图。如有歧义，用封闭式问题确认（最多 2-3 个问题）。提问时必须遵循**引导式提问原则**（见交互规范）。

### Phase 2: 目标拆解

将意图转化为 SMART 目标：

- **S**(Specific) — 具体到可执行
- **M**(Measurable) — 有明确的衡量标准
- **A**(Achievable) — 在约束条件内可达成
- **R**(Relevant) — 与真实意图直接相关
- **T**(Time-bound) — 有时间节点（如适用）

输出格式：

```
**核心目标**：[1-3 个]
**目标 1**：[SMART 描述]
  └── 关键结果 1.1：[可衡量的结果]
  └── 关键结果 1.2：[可衡量的结果]
```

### Phase 3: 维度设计

将每个目标拆解为可量化的维度。每个维度包含 7 个属性：

| 属性 | 必填 | 说明                                                                                           |
| ---- | :--: | ---------------------------------------------------------------------------------------------- |
| 名称 |  ✓   | 维度的唯一标识                                                                                 |
| 描述 |  ✓   | 这个维度衡量什么                                                                               |
| 类型 |  ✓   | 数值型/等级型/布尔型/范围型/选项型（详见 [dimension-types.md](references/dimension-types.md)） |
| 取值 |  ✓   | 具体的值域定义                                                                                 |
| 权重 |  -   | 重要程度（百分比或高/中/低）                                                                   |
| 基线 |  -   | 当前水平（如已知）                                                                             |
| 目标 |  -   | 期望达到的水平                                                                                 |

**维度设计原则**：

1. **MECE**：互斥且完全穷尽，不重叠不遗漏
2. **可观测**：每个维度必须有明确的数据采集方式
3. **适粒度**：不过粗（无法区分）也不过细（噪音太多），一般 3-7 个维度为宜
4. **有层次**：支持"大维度 → 子维度"的层级结构

### Phase 4: 评估体系

基于维度生成评估框架：

1. **评分标准**：每个维度的每个等级需要具体的判定标准（不是模糊的"好/差"）
2. **数据采集方式**：定义每个维度的数据来源（观察/测试/问卷/自动采集…）
3. **评估模板**：生成结构化的评估表，可直接用于实际评估

评估表格式：

```
| 维度 | 权重 | 评分 | 数据来源 | 说明 |
|------|------|------|----------|------|
| xxx  | 30%  | 良好 | 口述复述 | 具体表现描述 |
```

### Phase 5: 数据落地（生成领域 Skill）

Phase 1-4 的所有分析结果**以 Skill 形式落地**，而不是单纯的文档。生成模板详见 [skill-template.md](references/skill-template.md)。

#### 输出物：一个完整的领域 Skill

```
{领域名称}/                           # 如：合同审查/
├── SKILL.md                          # 完整工作流（按模板自动生成）
├── references/
│   └── dimensions.md                 # 维度定义 + 评估标准
├── evaluations/                      # 评估记录
└── eval-reports/                     # eval-refine-loop 报告
```

同时注册到 `.cursor/skills/{领域名称}/SKILL.md`，使其可直接调用。

#### 生成规则

1. **dimensions.md**：将 Phase 1-4 的全部内容（意图分析 + 目标 + 维度定义 + 评估标准）写入 `references/dimensions.md`
2. **SKILL.md**：按 [skill-template.md](references/skill-template.md) 生成，包含：
   - 触发条件（frontmatter 的 name 和 description）
   - 完整的处理工作流（基于维度层级和审查顺序）
   - 综合评定规则（汇总各维度结果的聚合逻辑）
   - 结构化输出报告模板
   - 与 eval-refine-loop 的协作说明

#### Skill 经验库（dimension-architect 自身积累）

```
dimension-architect/
├── cases/                    # 经验库
│   ├── _index.md             # 索引（按领域分类，便于检索）
│   └── {领域}-{场景}.md      # 具体经验案例
```

#### 落地时机

| 阶段           | 落地内容            | 文件                                         |
| -------------- | ------------------- | -------------------------------------------- |
| Phase 1-3 完成 | 维度定义 + 评估标准 | `{领域}/references/dimensions.md`            |
| Phase 4 完成   | 工作流 Skill        | `{领域}/SKILL.md` + 注册到 `.cursor/skills/` |
| 每次评估后     | 评估记录            | `{领域}/evaluations/YYYY-MM-DD-{主题}.md`    |

## 操作类型判断

与用户交互时，先判断操作类型：

| 类型     | 触发示例                         | 行为                                          |
| -------- | -------------------------------- | --------------------------------------------- |
| 分析操作 | "帮我分析这个需求""设计评估维度" | 执行 5 层流水线，生成领域 Skill               |
| 评估操作 | "帮我评估一下""打个分"           | 读取已有维度定义，执行评估，落地评估记录      |
| 查询操作 | "看看目前的维度""分析进展如何"   | **只读已有数据，简要返回，不写文件**          |
| 迭代操作 | "这个维度不太对""加个新维度"     | 更新 `references/dimensions.md` 和 `SKILL.md` |

## 与其他 Skill 协作

本 Skill 的核心产出是**领域 Skill**，协作关系：

```
dimension-architect → 生成领域 Skill（如"合同审查"）
                       → 领域 Skill 处理实际任务
                         → eval-refine-loop 评估输出质量
                           → 反馈回 dimension-architect 优化维度
```

- `eval-refine-loop`：读取领域 Skill 的 `references/dimensions.md` 作为评估基准
- `deep-interactive-learning` 等其他 Skill：可引用领域 Skill 的维度定义

## 交互规范

### 引导式提问原则（最高优先级）

每次向用户提问或请求确认时，**禁止空问**，必须遵循「分析先行 → 选项引导 → 用户选择」模式：

#### 三步结构

1. **先展示自己的分析**：基于领域专业知识，先给出对该问题的判断和思考过程
2. **提供具体选项**：将可能的方向整理为 A/B/C 选项，每个选项附带简要的适用场景或利弊说明
3. **标注推荐 + 留出补充**：明确标注推荐选项及理由，最后留"或者你有其他补充？"

#### 正反例

**反例（禁止）**：

- ❌ "你审查的合同类型是什么？"（空洞提问，用户需要自己想）
- ❌ "有没有需要调整或补充的？"（没有给用户方向）
- ❌ "你觉得这个目标对吗？"（用户只能说对/不对，没有优化空间）

**正例（推荐）**：

- ✅ "关于合同类型范围，我分析有 3 个可能方向：**A.** 聚焦采购/销售类（适合起步，维度更精准）；**B.** 覆盖全类型（通用性强但粒度可能较粗）；**C.** 按类型建立子维度体系（最完善但工作量大）。基于你法务部门日常使用的场景，**我倾向推荐 B**，你觉得呢？"
- ✅ "目标拆解如上。我认为可能还有 2 个方向值得考虑：**补充方向 A**：加入合同商务条款合理性维度（比如付款条件、交付标准）；**补充方向 B**：加入合同流程效率维度（审查周转时间等）。你看要不要加入，或者你有其他想补充的？"

#### 适用范围

此原则适用于所有需要用户输入的场景，包括但不限于：

- Phase 1 意图确认时的澄清提问
- Phase 2 目标拆解后的确认与补充
- Phase 3 维度设计后的调整建议
- 任何需要用户做决策的节点

### 其他规范

1. **先分析后动手**：收到需求后先完成 Phase 1-2，确认意图和目标无误后再设计维度
2. **渐进式呈现**：每个 Phase 完成后简要反馈，不一次性输出所有内容
3. **用户确认点**：Phase 1（意图确认）和 Phase 3（维度确认）是两个关键确认点，须用户确认后继续
4. **维度类型详解**：参见 [dimension-types.md](references/dimension-types.md)
5. **行业示例**：参见 [examples.md](references/examples.md)

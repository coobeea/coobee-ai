# 酒馆任务执行流程改造 - 需求分析

> 创建时间：2026-04-01  
> 需求来源：用户反馈  
> 优先级：P0（核心流程缺失）

---

## 需求背景

### 当前问题

酒馆任务系统（Tavern Task）是 coobee-ai 中实现 Agent 自主接单执行的核心模块。用户可以发布任务到"酒馆"，系统自动分配给 Agent 执行。

**当前执行流程过于简化**：

```
用户发布任务
  ↓
TaskScheduler 轮询检测
  ↓
创建 Thread → 分发给 Agent
  ↓
Agent 直接执行 → 提交结果
```

**核心问题**：

1. ❌ **没有需求分析阶段**：Agent 拿到任务就直接开始做，没有理解需求本质
2. ❌ **没有方案设计阶段**：没有评估多种技术方案，没有权衡利弊
3. ❌ **没有反思优化阶段**：没有自我审查方案的边界情况、安全隐患
4. ❌ **没有待办跟踪**：任务执行过程不透明，无法跟踪进度
5. ❌ **没有验收标准**：任务"完成"的标准不明确，质量无保障
6. ❌ **没有问题记录**：执行过程中遇到的 Bug 没有系统化管理
7. ❌ **没有综合报告**：任务完成后没有完整的交付物

**实际案例**：

| 任务                 | 当前问题                                     | 期望                                                |
| -------------------- | -------------------------------------------- | --------------------------------------------------- |
| "优化数据库查询性能" | Agent 直接改代码，可能引入新 Bug             | 先分析瓶颈 → 设计 3 种方案 → 选择最优 → 逐步实施    |
| "添加用户认证"       | Agent 可能遗漏边界情况（重复登录、会话过期） | 先评估安全风险 → 设计方案 → 反思漏洞 → 逐项验证     |
| "重构某模块"         | 改动范围不明确，可能影响其他功能             | 先分析影响范围 → 设计迁移方案 → 制定待办 → 逐步重构 |

## 核心目标

### 目标 1：标准化任务执行流程

引入**五阶段工作流**（参考 `poc-lifecycle`）：

```
阶段一：需求分析 → 01-需求分析.md
阶段二：方案设计 → 02-方案设计.md（上中下三策）
阶段三：反思优化 → 03-反思优化.md
阶段四：实施跟踪 → 04-TODO.md + 05-PROGRESS.md + 06-BUGS.md
阶段五：验收报告 → 07-验收报告.md + 08-综合报告.md
```

### 目标 2：提升任务执行质量

通过规范化流程确保：

- ✅ 需求理解准确（需求分析阶段）
- ✅ 方案选择合理（多方案对比）
- ✅ 边界情况考虑周全（反思优化）
- ✅ 执行过程透明可跟踪（进度文件）
- ✅ 质量有保障（验收标准）
- ✅ 问题系统化管理（Bug 记录）

### 目标 3：提供可追溯的执行记录

每个任务都有完整的文档链：

- 📄 为什么这样做（需求分析）
- 📄 考虑了哪些方案（方案设计）
- 📄 如何优化的（反思优化）
- 📄 做了哪些事（TODO + PROGRESS）
- 📄 遇到了什么问题（BUGS）
- 📄 最终交付了什么（验收报告）

## 约束条件

### 技术约束

1. **向后兼容**：现有简单任务仍可快速执行
2. **性能要求**：五阶段流程不应显著增加首次响应时间
3. **存储空间**：文档文件需合理控制（单任务 < 10MB）

### 业务约束

1. **任务类型差异**：
   - 简单任务（如"查询今天天气"）→ 可选流程或简化流程
   - 复杂任务（如"重构认证模块"）→ 必须走完整流程

2. **用户交互**：
   - 需求分析阶段可能需要用户澄清
   - 方案设计阶段可能需要用户选择
   - 技术评估阶段可能需要用户补充资料

3. **时间限制**：
   - 用户期望任务"尽快完成"，但质量更重要
   - 文档生成不应成为瓶颈

### 系统约束

1. **Agent 能力**：依赖 LLM 的推理能力生成高质量文档
2. **工具支持**：Agent 需要有文件读写、代码编辑等工具
3. **存储位置**：文档需要持久化，重启后可恢复

## 功能需求

### FR-1: 五阶段执行流程

#### FR-1.1: 阶段一 - 需求分析

**触发时机**：TaskScheduler 检测到新的 pending 任务

**执行逻辑**：

1. 创建 Thread
2. 创建 `lifecycle/01-需求分析.md`
3. Agent 收到专门的 Prompt：

   ```
   请分析以下酒馆任务的需求：

   任务标题：[title]
   任务描述：[description]

   请按照以下结构完成需求分析，并将结果写入 lifecycle/01-需求分析.md：

   ## 需求背景
   [为什么要做这件事]

   ## 核心目标
   [要达成什么效果]

   ## 技术评估
   [是否有现成方案？是否需要用户补充资料？]

   ## 约束条件
   [时间、技术、资源限制]

   ## 涉及范围
   [模块、文件、接口]

   完成后，请使用 external_tavern_update_lifecycle 工具更新任务阶段为 "方案设计"。
   ```

**验收标准**：

- ✅ `lifecycle/01-需求分析.md` 文件存在
- ✅ 文件内容完整（包含所有必需章节）
- ✅ 任务状态更新为 `lifecycle-stage: requirement-analysis`
- ✅ 如果需要用户澄清，任务状态变为 `awaiting-input`

---

#### FR-1.2: 阶段二 - 方案设计

**触发时机**：阶段一完成后

**执行逻辑**：

1. Agent 读取 `01-需求分析.md`
2. 生成上中下三策方案
3. 写入 `lifecycle/02-方案设计.md`
4. 如果任务配置为 `auto-select-solution: true`，自动选择中策
5. 否则，通知用户选择方案（任务状态 → `awaiting-decision`）

**方案结构**：

| 层次 | 名称     | 特点                                 |
| ---- | -------- | ------------------------------------ |
| 上策 | 最优方案 | 架构最优，长远收益高，实施成本较大   |
| 中策 | 平衡方案 | 兼顾质量和效率，推荐大多数场景       |
| 下策 | 最小方案 | 最快实现，适合紧急场景，可能留技术债 |

**验收标准**：

- ✅ `lifecycle/02-方案设计.md` 文件存在
- ✅ 包含上中下三个方案
- ✅ 每个方案包含：核心思路、改动范围、优劣对比
- ✅ 任务状态更新为 `lifecycle-stage: solution-design`

---

#### FR-1.3: 阶段三 - 反思优化

**触发时机**：方案选定后

**执行逻辑**：

1. Agent 读取选定方案
2. 自我审查（Self-Reflection）：
   - 边界情况检查
   - 安全隐患评估
   - 对现有功能的影响
   - 性能和可维护性评估
3. 生成优化建议
4. 写入 `lifecycle/03-反思优化.md`
5. 确定最终实施方案

**验收标准**：

- ✅ `lifecycle/03-反思优化.md` 文件存在
- ✅ 包含边界情况、安全评估、影响分析、优化调整
- ✅ 明确最终方案
- ✅ 任务状态更新为 `lifecycle-stage: reflection`

---

#### FR-1.4: 阶段四 - 实施跟踪

**触发时机**：反思优化完成后

**执行逻辑**：

1. Agent 根据最终方案生成待办事项
2. 创建三个跟踪文件：
   - `lifecycle/04-TODO.md`：待办列表 + 验收标准
   - `lifecycle/05-PROGRESS.md`：执行进度日志
   - `lifecycle/06-BUGS.md`：问题记录
3. 逐项执行待办：
   - 每完成一项 → 更新 TODO 状态 + 追加 PROGRESS 记录
   - 遇到问题 → 记录到 BUGS
   - 每项完成后 → 执行验收标准中的测试
4. 所有待办完成后 → 进入阶段五

**验收标准**：

- ✅ 三个文件都存在
- ✅ TODO 中每项都有明确的验收标准
- ✅ PROGRESS 记录每次变更
- ✅ BUGS 记录遇到的问题及解决方案
- ✅ 所有 TODO 项标记为已完成

---

#### FR-1.5: 阶段五 - 验收报告

**触发时机**：所有待办完成后

**执行逻辑**：

1. Agent 执行整体验收：
   - 检查每个 TODO 的验收标准是否通过
   - 检查 BUGS 中是否有未解决的阻塞问题
   - 生成测试报告
2. 创建验收文档：
   - `lifecycle/07-验收报告.md`：逐项验收结果
   - `lifecycle/08-综合报告.md`：任务摘要、技术亮点、交付清单
3. 更新酒馆任务状态 → `completed`
4. 发送完成通知

**验收标准**：

- ✅ `lifecycle/07-验收报告.md` 存在
- ✅ `lifecycle/08-综合报告.md` 存在
- ✅ 所有待办项验收通过
- ✅ 酒馆任务状态为 `completed`
- ✅ 用户收到完成通知

## 非功能需求

### NFR-1: 技术评估与用户交互

**需求**：在需求分析阶段，Agent 需要评估：

1. 技术可行性：当前系统能否解决？
2. 资料完整性：是否需要用户补充文档、数据、API 密钥等？

**实现方式**：

- Agent 在 `01-需求分析.md` 的 `技术评估` 章节明确说明
- 如果需要用户补充：
  - 任务状态 → `awaiting-input`
  - 发送通知：「任务「xxx」需要补充资料」
  - 在任务详情页显示"待补充资料"列表
  - 用户补充后，点击"继续执行"，任务状态 → `in-progress`

**验收标准**：

- ✅ 技术评估准确（不遗漏缺失的依赖/资源）
- ✅ 需要补充资料时，任务正确暂停
- ✅ 用户补充后，任务正确恢复

---

### NFR-2: 方案选择机制

**需求**：在方案设计阶段，支持两种模式：

1. **自动选择**：Agent 自动选择中策（默认）
2. **用户选择**：Agent 生成三策后，暂停等待用户决策

**配置方式**：

- 任务创建时指定 `config.autoSelectSolution: boolean`
- 或在应用配置中设置全局默认值

**验收标准**：

- ✅ 自动模式下，Agent 选择中策并说明理由
- ✅ 手动模式下，任务暂停，用户收到"请选择方案"通知
- ✅ 用户选择后，任务恢复执行

---

### NFR-3: 进度透明化

**需求**：用户能够实时查看任务执行进度

**实现方式**：

1. 前端任务详情页新增"执行进度"Tab
2. 显示内容：
   - 当前阶段（需求分析/方案设计/反思/执行/验收）
   - 当前待办（如果在阶段四）
   - 完成度百分比
   - 最新进度日志
3. 实时更新（通过 WebSocket 推送）

**验收标准**：

- ✅ 用户能看到当前阶段
- ✅ 用户能看到完成度
- ✅ 用户能看到最新进度
- ✅ 更新延迟 < 2 秒

---

### NFR-4: 文档规范化

**需求**：所有阶段文档遵循统一格式

**规范要求**：

- ✅ 文件名：`01-需求分析.md` ~ `08-综合报告.md`（编号固定）
- ✅ 存放位置：`{workspace}/lifecycle/`
- ✅ 格式：Markdown，包含 YAML Front Matter（创建时间、状态等）
- ✅ 内容完整：每个阶段的必需章节不可省略

**验收标准**：

- ✅ 所有文档文件名符合规范
- ✅ 文档内容结构完整
- ✅ 文档可被前端正确解析和展示

---

### NFR-5: 验收标准量化

**需求**：每个 TODO 项必须有可验证的验收标准

**标准要求**：

- ❌ **不可接受**：「完成用户认证功能」（标准不明确）
- ✅ **可接受**：
  - 用户可以通过用户名密码登录
  - 登录失败 3 次后锁定账号 5 分钟
  - 登录成功后返回 JWT Token
  - Token 过期时间为 24 小时
  - 测试代码：`src/auth/__tests__/login.test.ts`

**验收标准**：

- ✅ 每个 TODO 项至少有 2 条可量化标准
- ✅ 验收标准可通过代码测试验证
- ✅ 验收标准写明测试文件路径

## 风险评估

### 风险 1：执行时间延长 🔴

**风险**：五阶段流程会增加任务执行时间

**影响**：

- 简单任务原本 30 秒完成，现在可能需要 2-3 分钟
- 用户可能认为系统"变慢了"

**缓解措施**：

- ✅ 提供"快速模式"（简单任务自动识别并跳过某些阶段）
- ✅ 前端明确展示"正在分析需求"等阶段提示，增强感知
- ✅ 异步执行，不阻塞用户其他操作

---

### 风险 2：LLM 生成文档质量不稳定 🟡

**风险**：Agent 生成的需求分析、方案设计可能不准确

**影响**：

- 文档流于形式，无实际价值
- 方案设计不合理，导致后续执行失败

**缓解措施**：

- ✅ 提供详细的文档模板和示例
- ✅ 引入 Self-Reflection 阶段强制自我审查
- ✅ 关键阶段加入人工审查（awaiting-decision）

---

### 风险 3：存储空间增长 🟢

**风险**：每个任务生成 8 个文档文件，占用存储

**影响**：

- 100 个任务 → 800 个文件
- 预计每个任务文档总大小 < 500KB
- 100 个任务 → 50MB（可接受）

**缓解措施**：

- ✅ 定期清理已完成任务的文档（保留 30 天）
- ✅ 压缩归档历史任务
- ✅ 提供用户手动删除功能

---

### 风险 4：向后兼容性 🟡

**风险**：现有的简单任务执行逻辑被破坏

**影响**：

- 正在执行的任务可能中断
- 旧版本创建的任务无法恢复

**缓解措施**：

- ✅ 检测任务是否已有 `lifecycle/` 目录，决定使用新旧流程
- ✅ 提供配置项：`tavern.useLifecycleFlow: boolean`（默认 true）
- ✅ 旧任务自动标记为"传统模式"，不强制迁移

## 附录：当前代码分析

### 现有 TaskScheduler.dispatchTask() 流程

```typescript
// src/main/ai/tavern/TaskScheduler.ts:168-235
private async dispatchTask(task: Task): Promise<void> {
  // 1. 更新状态为 in-progress
  await store.updateTask(task.id, { status: 'in-progress' });

  // 2. 创建 Thread
  const thread = await threadStore.create({
    title: `[Task] ${task.title}`,
    agentId: 'default',
    // ...
  });

  // 3. 写入 GOAL.md（简单目标文件）
  await this.writeTaskGoalFile(sessionId, task);

  // 4. 构造消息
  const message = this.buildTaskMessage(task);

  // 5. 提交给 AgentExecutor
  await agentExecutor.submitViaPipeline(sessionId, message, 'agent');

  // 6. 等待执行完成（通过 stream:end 事件）
}
```

**问题点**：

- ❌ 直接进入执行，没有分析和设计阶段
- ❌ `buildTaskMessage()` 只是简单拼接任务描述
- ❌ `GOAL.md` 内容过于简单
- ❌ 没有待办跟踪机制

---

### 改造点

| 改造项                   | 改造内容                                           |
| ------------------------ | -------------------------------------------------- |
| `dispatchTask()`         | 不再直接执行，而是调用 `LifecycleExecutor.start()` |
| `buildTaskMessage()`     | 拆分为 5 个阶段的 Prompt 模板                      |
| `writeTaskGoalFile()`    | 删除（由阶段化流程生成文档替代）                   |
| 新增 `LifecycleExecutor` | 五阶段状态机 + 阶段切换逻辑                        |

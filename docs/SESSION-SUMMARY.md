## 🎯 核心设计

### 1️⃣ 全自主智能体系统（P0 - 最高优先级）🚀

#### 核心愿景（用户原话）

> **"我要的不是一个聊天助手，也不是一个方案生成器，而是一个能把我模糊想法，全自动变成可上线、可运行、可交付的真实产品的自主执行智能体。"**

#### 六大核心诉求

| 诉求              | 说明                               | 当前系统 | 目标系统 |
| ----------------- | ---------------------------------- | -------- | -------- |
| **1. 极简输入**   | 只需模糊想法，无需明确目标/步骤    | ❌       | ✅       |
| **2. 全流程自主** | 从理解到发布，全程无需人工干预     | ❌       | ✅       |
| **3. 真实产物**   | 产出可直接使用的产品，而非中间文档 | ⚠️       | ✅       |
| **4. 自主迭代**   | 自己验证、优化、修复，无需人工决策 | ❌       | ✅       |
| **5. 极简汇报**   | 完成后一份简洁总结，不打扰用户     | ❌       | ✅       |
| **6. 端到端落地** | 从想法到可运行产品的完整闭环       | ❌       | ✅       |

#### 全新架构（6 层）

```
用户交互层
  └─ MinimalInput + TaskDashboard + ArtifactGallery

意图理解层 ⭐
  └─ IntentParser（深度推理，提取真实意图）
  └─ ContextEnricher（自动搜索相关信息）

任务规划层 ⭐
  └─ TaskPlanner（目标拆解 + DAG 生成）
  └─ FeasibilityEvaluator（可行性评估）

执行编排层
  └─ ExecutionOrchestrator（资源调度）
  └─ AgentTeamManager（动态组建团队）

执行引擎层 ⭐⭐⭐（核心）
  └─ AutonomousEngine（自主循环）
      while (!isGoalAchieved()) {
        step = planNextStep()
        result = executeStep()
        validation = validateResult()
        if (!validation.passed) {
          result = selfRepair(result, validation)

        updateState(result)
      }

产物管理层
  └─ ArtifactRepository（统一存储 + 版本控制）
  └─ PublishManager（自动发布到外部平台）
```

#### 当前系统的根本性问题

| 问题             | 具体表现                   | 是否可通过优化解决 |
| ---------------- | -------------------------- | ------------------ |
| **交互模式错误** | 对话驱动，需要多轮交互     | ❌ 需要全新架构    |
| **缺少任务抽象** | 没有"任务"概念，只有"对话" | ❌ 需要全新架构    |
| **产出分散**     | 文件在工作空间，对话在历史 | ❌ 需要产物管理层  |
| **缺少自主性**   | HITL 审批，无法全自动      | ⚠️ 可部分改造      |
| **缺少验证机制** | 无自动质量验证             | ✅ 可增量添加      |
| **缺少迭代能力** | 对话结束即终止             | ❌ 需要自主循环    |
| **缺少外部集成** | 无法自动发布到外部平台     | ✅ 可增量添加      |

**结论**：当前对话驱动架构**无法支撑自主执行愿景**，必须构建全新系统。

### 2️⃣ 模型组与自动选择（P1）🔥

#### 核心功能

**解决配额和稳定性问题**：

```typescript
// Agent 配置模型组（而非单个模型）
{
  "model": "@high-performance"  // 引用模型组
}

// 模型组配置（自动负载均衡）
{
  "high-performance": {
    "strategy": "quota-aware",  // 配额感知
    "models": [
      "openai/gpt-4o",
      "anthropic/claude-3-5-sonnet",
      "google/gemini-2.0-flash-thinking"
    ]
  }
}

// 系统行为
→ 检查三个模型的配额
→ 优先使用配额最充足的
→ 配额不足时自动切换
→ API 故障时自动 fallback
```

#### 五种负载均衡策略

- **round-robin**：轮询使用组内模型
- **random**：随机选择
- **weighted**：加权选择
- **quota-aware**：配额感知（优先用配额充足的）⭐
- **fallback**：故障转移（失败后自动尝试下一个）⭐

#### 实施计划（3-5 天）

```
Phase 1: 基础架构（2-3 天）
Phase 2: Agent 集成（1-2 天）
Phase 3: 前端 UI（1-2 天）
Phase 4: 配额集成（可选，1 天）
```

### 3️⃣ 架构深度分析（P2-P3）⭐

#### 识别的 9 个结构性问题

1. Runtime 职责过重（1500+ 行）
2. Gateway 协议不统一（WS/HTTP/SSE 混用）
3. 前端 Store 碎片化（10 个 Store）
4. 配置分散（4 处配置源）
5. 工具系统缺少抽象
6. 事件系统类型不安全
7. 缺少日志查询接口
8. 缺少统一错误处理
9. 缺少性能监控

#### 快速见效方案（Sprint 1，3-5 天）

```
✅ 统一错误处理（AppError 类型体系）

✅ 日志查询接口（LogService）
```

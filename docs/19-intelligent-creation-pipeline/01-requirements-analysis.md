# 智能创建流水线 — 需求分析文档

> 版本：v1.0 | 日期：2026-03-06 | 状态：讨论中

## 1. 问题陈述

### 1.1 现状

当前系统中 Skill 和 Agent 的创建流程**过于简化**：

| 创建方式       | 流程                                        | 产物               | 问题                               |
| -------------- | ------------------------------------------- | ------------------ | ---------------------------------- |
| AI 创建 Skill  | 用户输入一段文字 → SSE 生成 → 写入 SKILL.md | 单个 Markdown 文件 | 缺乏意图分析、维度校验、迭代优化   |
| AI 创建 Agent  | 用户输入一段文字 → SSE 生成 → 写入 JSON     | 单个配置 JSON      | 缺乏能力规划、Skill 编排、质量验证 |
| 手动创建 Agent | 填写表单（名称、描述、指令）                | 单个配置 JSON      | 门槛高、无指导、无反馈             |

**核心痛点**：从「用户一句话」到「可用产物」之间缺失了大量关键步骤——需求澄清、方案设计、质量校验、迭代改进。这些步骤在传统软件工程中是标准实践，在 AI Agent/Skill 创建中同样不可或缺。

### 1.2 期望

建立一套**标准化的智能创建流水线**，使得：

- **Skill 创建**：经过需求分析 → 方案设计 → 实施 → 校验 → 迭代的完整流程
- **Agent 创建**：在 Skill 的基础上，增加人格设计、Skill 编排、协作策略等环节
- **两者共享**同一套流水线框架，根据创建对象的不同走不同的分支

## 2. 深度分析

### 2.1 创建复杂度的层次

```
┌─────────────────────────────────────────────────────────┐
│                   Agent（智能体）                         │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐   │
│  │ Skill A  │ │ Skill B  │ │ Skill C  │ │   ...    │   │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘   │
│  + 人格定义（IDENTITY / SOUL / USER）                     │
│  + Skill 编排策略                                        │
│  + 模型配置与备选策略                                     │
│  + 协作 / 委托规则                                        │
└─────────────────────────────────────────────────────────┘
```

**关键认知**：

1. **Skill** 是最小的能力单元——一段场景化操作手册，教 Agent "如何做某件事"
2. **Agent** 是 Skill 的编排容器——组合多个 Skill、赋予人格、配置模型，形成一个"角色"
3. **训练** 是让 Agent 在特定 Skill 上持续改进——积累 `skill-data/` 中的经验数据

三者的关系：

```
创建 Skill → 创建 Agent（关联 Skill） → 训练 Agent（在 Skill 维度上迭代）
```

### 2.2 为什么「一句话创建」不够

以创建一个"销售话术分析 Skill"为例：

| 步骤     | 一句话创建（现状）     | 完整流水线（期望）                                        |
| -------- | ---------------------- | --------------------------------------------------------- |
| 需求理解 | 直接猜测用户意图       | 多轮对话澄清：分析什么？输入是什么格式？输出要什么结构？  |
| 验收标准 | 无                     | 生成量化维度：准确率、覆盖率、格式规范度等                |
| 方案设计 | 直接生成一个版本       | 生成 2-3 个方案，从不同角度（关注点、粒度、输出格式）对比 |
| 实施     | 一次性写完             | 分步骤生成：先框架、再填充、逐节完善                      |
| 验证     | 无                     | 用预设的测试用例 + 验收标准进行自检                       |
| 迭代     | 无（生成什么就是什么） | 根据验证结果迭代 2-3 轮，直到达标                         |

### 2.3 流水线抽象

无论是 Skill 还是 Agent，其创建过程可以抽象为以下阶段：

```
Phase 1: 需求分析（Requirements Analysis）
    ├── 意图澄清：多轮对话，理解用户真实需求
    ├── 边界定义：明确做什么、不做什么
    ├── 验收标准：生成量化的校验维度
    └── 产出：需求文档 + 验收标准

Phase 2: 方案设计（Solution Design）
    ├── 生成多个候选方案（2-3个）
    ├── 方案对比分析（优劣势、适用场景）
    ├── 用户选择 / 合并 / 定制
    └── 产出：确定方案 + 设计文档

Phase 3: 实施生成（Implementation）
    ├── 按方案逐步生成产物
    ├── 每步完成后基于验收标准自检
    ├── 失败则回退修正（最多 3 次）
    └── 产出：初版 Skill/Agent 定义

Phase 4: 验证测试（Validation）
    ├── 基于验收标准的自动化验证
    ├── 实际场景模拟测试
    ├── 生成验证报告
    └── 产出：测试报告 + 通过/不通过结论

Phase 5: 迭代优化（Iteration）
    ├── 根据验证报告分析薄弱点
    ├── 可选择重跑 Phase 2-4（生成 V2）
    ├── 多版本对比，选择最优
    └── 产出：最终版本

Phase 6: 发布 & 存档（Release）
    ├── 写入最终产物到文件系统
    ├── 存档创建过程（需求文档 + 方案 + 测试报告）
    └── 产出：可用的 Skill/Agent + 过程文档
```

## 3. 核心设计思路

### 3.1 统一的创建引擎 vs 分离的创建器

**方案 A：统一创建引擎（推荐）**

```
┌──────────────────────────────────────────────┐
│          CreationPipeline（创建流水线）         │
│                                              │
│  Phase 1 ─→ Phase 2 ─→ Phase 3 ─→ ...      │
│                                              │
│  ┌─────────────┐    ┌────────────────┐       │
│  │ SkillBuilder │    │ AgentBuilder   │       │
│  │ (Skill 专用  │    │ (Agent 专用    │       │
│  │  生成逻辑)   │    │  生成逻辑)     │       │
│  └─────────────┘    └────────────────┘       │
│                                              │
│  共享：需求分析、方案对比、验证测试、迭代引擎    │
└──────────────────────────────────────────────┘
```

**优势**：

- 流程框架统一，维护成本低
- Skill 和 Agent 创建共享需求分析、验证测试等通用能力
- 创建 Agent 时可以内嵌 Skill 创建子流程

**方案 B：独立的 SkillCreator 和 AgentCreator**

各自实现完整流程。代码重复度高，不推荐。

### 3.2 需求分析：流水线最关键的一步

需求分析阶段的质量直接决定了后续所有步骤的质量。这一步需要：

**3.2.1 多轮对话式意图澄清**

不是一次性收集所有信息，而是通过对话逐步深入：

```
Round 1: 基础意图
  "你想创建什么类型的 Skill/Agent？主要解决什么问题？"

Round 2: 场景细化
  "这个能力在什么场景下使用？输入是什么，期望输出是什么？"

Round 3: 边界确认
  "有哪些情况是不需要处理的？有什么限制条件？"

Round 4: 验收标准
  "怎么判断创建出来的结果是好的？有哪些关键指标？"
```

**3.2.2 自动生成验收标准**

基于需求分析的结果，利用 `dimension-architect` Skill 的能力，自动生成量化的验收维度：

```json
{
  "dimensions": [
    { "key": "accuracy", "label": "准确性", "weight": 0.3, "standard": "核心功能覆盖率 ≥ 90%" },
    { "key": "completeness", "label": "完整度", "weight": 0.25, "standard": "所有定义的场景均有处理逻辑" },
    { "key": "format", "label": "格式规范", "weight": 0.15, "standard": "符合 SKILL.md 结构规范" },
    { "key": "usability", "label": "可用性", "weight": 0.2, "standard": "无需额外说明即可使用" },
    { "key": "robustness", "label": "鲁棒性", "weight": 0.1, "standard": "边界情况有明确处理" }
  ]
}
```

这套验收标准会贯穿后续的所有阶段：生成时参照、验证时度量、迭代时改进。

### 3.3 Skill 创建的具体产物

当前 Skill 只有一个 `SKILL.md` 文件。流水线创建应该产出更丰富的结构：

```
skills/{skill-name}/
├── SKILL.md              # 主文件（最终产物）
├── .creation/            # 创建过程存档
│   ├── requirements.md   # 需求分析文档
│   ├── criteria.json     # 验收标准
│   ├── designs/          # 候选方案
│   │   ├── plan-a.md
│   │   ├── plan-b.md
│   │   └── comparison.md
│   ├── versions/         # 历史版本
│   │   ├── v1/
│   │   └── v2/
│   └── validation/       # 测试报告
│       ├── report-v1.md
│       └── report-v2.md
├── references/           # 参考资料
├── scripts/              # 辅助脚本
└── test-cases/           # 测试用例（用于后续迭代验证）
```

### 3.4 Agent 创建的具体产物

Agent 的创建产物更加丰富，因为它涉及人格文件和 Skill 编排：

```
agents/{agentId}.json     # Agent 定义（最终产物）

homes/{agentId}/          # Agent Home（生成/更新的文件）
├── IDENTITY.md           # 身份定义（由流水线生成/优化）
├── SOUL.md               # 性格与价值观
├── USER.md               # 用户画像
├── NOTES.md              # 工作笔记模板
├── AGENTS.md             # 可协作的 Agent 列表
├── memory/               # 记忆存储
├── skill-data/           # Skill 产出数据
└── .creation/            # 创建过程存档（同 Skill）
    ├── requirements.md
    ├── criteria.json
    ├── persona-design.md # 人格设计方案
    ├── skill-plan.md     # Skill 编排策略
    └── validation/
```

### 3.5 与现有训练系统的关系

```
                     创建                  训练                  进化
                     ──→                  ──→                  ──→

  ┌──────────┐    ┌──────────┐    ┌──────────────┐    ┌──────────┐
  │ 用户需求  │ → │ 创建流水线 │ → │ 初版 Skill/  │ → │ 训练系统  │
  │          │    │ (本方案)  │    │ Agent        │    │ (已有)   │
  └──────────┘    └──────────┘    └──────────────┘    └──────────┘
                                                            │
                                                            ↓
                                                    ┌──────────────┐
                                                    │ 训练后改进版  │
                                                    │ (skill-data  │
                                                    │  经验积累)    │
                                                    └──────────────┘
```

**关系定位**：

- **创建流水线** = 从 0 到 1，生成初版
- **训练系统** = 从 1 到 N，在实际数据上持续改进
- 创建流水线的**验收标准**可以直接被训练系统复用作为**训练目标维度**
- 训练系统的**改进建议**可以反哺到创建流水线的**迭代优化**阶段

### 3.6 可标准化 vs 需定制化的部分

| 阶段              | 标准化程度                      | 说明                                              |
| ----------------- | ------------------------------- | ------------------------------------------------- |
| Phase 1: 需求分析 | **低** — 高度定制化             | 每个 Skill/Agent 的需求都不同，需要灵活的对话引导 |
| Phase 2: 方案设计 | **中** — 框架标准化、内容定制化 | 方案对比模板可以标准化，但具体方案内容需定制      |
| Phase 3: 实施生成 | **高** — 基本可标准化           | 文件生成、格式校验、目录结构等都可以模板化        |
| Phase 4: 验证测试 | **高** — 基本可标准化           | 基于验收标准的评分逻辑可以复用                    |
| Phase 5: 迭代优化 | **中** — 流程标准化、策略定制化 | 迭代框架固定，但优化方向需要根据验证结果动态决定  |
| Phase 6: 发布存档 | **高** — 完全标准化             | 文件写入、目录创建、索引更新等                    |

## 4. 技术架构概念

### 4.1 后端架构

```
src/main/creation/
├── CreationPipeline.ts       # 流水线引擎（Phase 调度）
├── PhaseRunner.ts            # 阶段执行器
├── phases/
│   ├── RequirementsPhase.ts  # Phase 1: 需求分析
│   ├── DesignPhase.ts        # Phase 2: 方案设计
│   ├── ImplementPhase.ts     # Phase 3: 实施生成
│   ├── ValidatePhase.ts      # Phase 4: 验证测试
│   ├── IteratePhase.ts       # Phase 5: 迭代优化
│   └── ReleasePhase.ts       # Phase 6: 发布存档
├── builders/
│   ├── SkillBuilder.ts       # Skill 专用生成器
│   └── AgentBuilder.ts       # Agent 专用生成器
├── validators/
│   ├── CriteriaEvaluator.ts  # 验收标准评估器（复用 eval-refine-loop Skill）
│   └── TestRunner.ts         # 测试用例执行器
├── CreationStore.ts          # 创建过程持久化
└── types.ts                  # 类型定义
```

### 4.2 前端架构

```
src/renderer/src/
├── views/
│   └── CreationWizardView.vue    # 创建向导主视图
├── components/creation/
│   ├── RequirementsChat.vue      # Phase 1: 对话式需求收集
│   ├── DesignComparison.vue      # Phase 2: 方案对比面板
│   ├── ImplementProgress.vue     # Phase 3: 生成进度展示
│   ├── ValidationReport.vue      # Phase 4: 验证结果展示
│   ├── IterationPanel.vue        # Phase 5: 迭代控制
│   └── PhaseTimeline.vue         # 流水线进度时间线
└── api/
    └── creation.ts               # 创建流水线 API
```

### 4.3 核心交互模式

Phase 1（需求分析）采用**对话式**交互——用户和 AI 来回讨论，逐步明确需求。

Phase 2-6 采用**面板式**交互——展示 AI 的产出，用户确认/选择/调整后推进到下一步。

每个 Phase 之间有**检查点（Checkpoint）**，用户可以：

- **继续** → 进入下一阶段
- **返回** → 回到上一阶段修改
- **重跑** → 重新执行当前阶段（生成新版本）

## 6. 关键决策（已确认）

> 以下决策基于 2026-03-06 讨论结果。

### 6.1 创建粒度 — 需求驱动

**结论**：按用户需求来走。

- 用户说「创建 Skill」→ 流水线创建 Skill（可以是一个，也可以是一组相关的 Skill）
- 用户说「创建 Agent」→ 流水线创建 Agent（在需求分析阶段确定需要哪些 Skill，对缺失的 Skill 可以作为子任务创建）

Skill 本身是标准化的能力单元，流水线会确保每个 Skill 都经过完整的质量流程。当一次创建涉及多个 Skill 时，每个 Skill 独立走一遍 Phase 3-4（生成+验证），最终统一在 Phase 6 发布。

### 6.2 版本管理 — 复用训练系统 + 扩展

**结论**：复用 `TrainingVersionManager` 的版本概念，扩展为通用的 `VersionManager`。

创建流水线产出的每个版本（V1、V2...）记录在 `.creation/versions/` 中，与训练系统的版本纳入同一条时间线。这样从"创建 → 训练 → 改进"全过程都有完整的版本追溯。

### 6.3 协作创建 — 是，每个 Phase 由专业 Agent 执行

**结论**：支持多 Agent 协作。

每个 Phase 有对应的专业 Agent，由编排 Agent 按流程逐步调度。

### 6.4 架构模式 — 编排 Agent + 固定流程

**结论**：**流程固定，执行由 Agent 驱动**。

```
┌──────────────────────────────────────────────────────────┐
│           creation-orchestrator（编排 Agent）              │
│                                                          │
│  固定流程：Phase 1 → 2 → 3 → 4 → 5 → 6                  │
│                                                          │
│  每个 Phase 调用专业 Agent 执行：                          │
│  ┌─────────────┐ ┌──────────────┐ ┌──────────────┐      │
│  │ requirements │ │ solution-    │ │ skill/agent- │      │
│  │ -analyst    │ │ designer     │ │ builder      │      │
│  └─────────────┘ └──────────────┘ └──────────────┘      │
│  ┌─────────────┐ ┌──────────────┐ ┌──────────────┐      │
│  │ quality-    │ │ iteration-   │ │ release-     │      │
│  │ validator   │ │ optimizer    │ │ manager      │      │
│  └─────────────┘ └──────────────┘ └──────────────┘      │
│                                                          │
│  后端代码只管流程调度和状态持久化，不管具体业务逻辑         │
└──────────────────────────────────────────────────────────┘
```

**核心原则**：

- 后端代码（`CreationPipeline`）只负责：Phase 调度、状态管理、检查点、事件广播
- 每个 Phase 的业务逻辑由对应 Agent 通过 `ChannelRuntime.executeAgent` 执行
- Agent 可以被替换和升级，而流程框架保持稳定

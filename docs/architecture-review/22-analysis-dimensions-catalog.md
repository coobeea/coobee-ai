## 三、未执行维度

### Level 4: 用户视角

#### D-1: 端到端场景走查

**目标**: 模拟真实用户操作路径，验证全链路正确性

**关注点**:

- 首次启动 → 配置加载 → 第一次对话 → 收到回复 的完整链路
- 多轮对话 → 上下文保持 → 工具调用 → 结果返回
- 切换 Provider → 热重载 → 新 Provider 生效
- 长时间挂机 → 内存状态 → 重新操作
- 同时打开多个 Tab → 多 Session 并行

**预期发现**: 链路断裂点、状态不一致、用户可感知的 Bug

---

#### D-2: 边缘用例与防御性

**目标**: 验证异常输入、极端场景下的系统行为

**关注点**:

- 超长消息（100K+ 字符）
- 空消息、纯空格消息、特殊字符
- API Key 错误/过期/额度用完
- 网络中断/超时/半连接
- 配置文件被删除/清空/格式损坏
- 磁盘空间不足
- Provider 全部禁用

**预期发现**: 未处理的边界条件、crash、无提示的失败

---

#### D-3: 前端状态管理

**目标**: 审查 Renderer 进程的状态管理、IPC 通信、UI 一致性

**关注点**:

- Pinia Store 的状态一致性（乐观更新+回滚）
- WebSocket 断连后的自动重连与消息补发
- 流式消息的渲染性能（大量 chunk 的 DOM 更新）
- 路由切换时的组件生命周期清理
- IPC 调用的 loading/error 状态管理

**预期发现**: 状态不一致、内存泄漏、UI 闪烁

---

### Level 3: 运行时行为

#### D-4: 资源泄漏专项

**目标**: 系统化检查所有资源的分配/释放配对

**关注点**:

- EventListener 注册/移除配对
- setInterval/setTimeout 的清理
- AbortController 的生命周期
- 文件句柄（fs.open/close）
- chokidar watcher
- WebSocket 连接

**预期发现**: 长时间运行后的内存增长、句柄泄漏

---

#### D-5: 错误传播与恢复策略

**目标**: 审查"错误发生后系统能否恢复到可用状态"

**关注点**:

- LLM API 返回 500 后，下次请求能否正常工作
- 工具执行崩溃后，Agent run 能否优雅结束
- Config 热重载失败后，系统是否仍使用上次有效配置
- Extension Hook 抛错后，主流程是否不受影响
- Electron 主进程 uncaughtException 处理

**预期发现**: 不可恢复的错误状态、需要重启才能解决的问题

---

#### D-6: 并发压力场景

**目标**: 模拟高频操作，验证并发安全

**关注点**:

- 用户快速连续发送 10 条消息
- 同时 abort + 发送新消息
- 多个 Tab 同时操作同一 Session
- 配置文件被外部编辑器快速保存多次
- 多个 Extension 同时注册 Hook

**预期发现**: 竞态条件、队列溢出、状态混乱

---

### Level 2: 架构结构

#### D-7: Extension 体系完整性

**目标**: 审查 Extension 系统的设计完整性和扩展能力

**关注点**:

- Extension 注册/发现/加载生命周期
- Hook 点覆盖是否充分（before/after 对称性）
- Extension 间的冲突解决（同名 Hook、同名工具）
- Extension 的隔离性（一个 Extension 崩溃不影响其他）
- Extension API 的版本兼容性

**预期发现**: 扩展点不足、隔离性差、生命周期不完整

---

#### D-8: 数据模型与持久化

**目标**: 审查数据的存储、序列化、迁移策略

**关注点**:

- 会话历史的存储格式和查询效率
- 配置文件的 schema 版本迁移
- StreamStore 的存储容量和清理策略
- 上下文快照的格式和兼容性
- 数据丢失风险（非原子操作、无备份）

**预期发现**: 数据格式不一致、迁移困难、存储膨胀

---

### Level 1: 代码基础

#### D-9: 类型安全专项

**目标**: 消除 `as any`、`as unknown`、`@ts-ignore` 等类型逃逸

**关注点**:

- 统计所有 `as any` 和 `as unknown` 的使用
- 检查泛型参数的正确性
- Zod schema 与 TypeScript 类型的一致性
- 第三方库类型定义的完整性

**预期发现**: 类型安全漏洞、运行时类型错误

---

#### D-10: 测试覆盖与质量

**目标**: 评估测试体系的完整性和有效性

**关注点**:

- 关键路径的测试覆盖率
- Mock 的准确性（是否与真实行为一致）
- 集成测试的场景覆盖
- 测试与实际代码的同步维护
- 难以测试的模块（Electron 依赖、全局单例）

**预期发现**: 覆盖率盲区、误导性的测试、脆弱测试

## 六、分析成熟度模型

```
Level 0: 功能实现    ← 第 1-4 轮已完成
Level 1: 基础健康    ← 第 5-8 轮已完成（子系统纵向）
Level 2: 深层质量    ← 第 9-10 轮已完成（横切面 + 契约/边界/时序）
Level 3: 运行时正确  ← 下一步目标（端到端 + 错误恢复 + 资源管理）
Level 4: 生产就绪    ← 最终目标（压力测试 + 边缘用例 + 前端完整性）
```

每个 Level 都建立在前一个 Level 的基础上。当前项目处于 **Level 2 → Level 3 过渡阶段**。

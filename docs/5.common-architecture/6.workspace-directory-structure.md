# Agent 工作空间目录结构设计

本文档定义 coobee-ai 系统中主 Agent 和各类子 Agent 的完整目录结构规范。

## 概述

每个 Agent 拥有独立的工作空间，用于存储会话历史、上下文快照、事件流、技能和输出文件。

工作空间根目录位于 `{userHome}/workspaces/`，每个 Agent 按其身份隔离：

- 主 Agent：在顶层创建独立 workspace
- 子 Agent：嵌套在父 Agent workspace 的 tasks 目录下

## 主 Agent 工作空间

主 Agent 直接与用户交互，其 workspace 位于顶层。

### 目录结构

```
{userHome}/workspaces/{threadId}/
├── GOAL.md                    ← 目标文件（系统初始化时创建，Agent 填写）
├── sessions/
│   └── {sessionId}/
│       └── messages.jsonl
├── contexts/
│   ├── 2026-02-21T10-00-05-123.json
│   ├── 2026-02-21T10-05-32-456.json
│   └── ...
├── events/
│   └── events.jsonl
├── skills/
│   ├── custom-skill-1/
│   │   └── SKILL.md
│   └── ...
├── extensions/
│   ├── custom-extension-1/
│   │   ├── extension.json
│   │   └── index.ts
│   └── ...
├── output/
│   ├── report.md
│   ├── diagram.png
│   └── ...
├── logs/
│   └── agent.log
├── memory/
│   └── notes.md
├── tasks/
│   └── (子 Agent 任务目录，见下文)
└── checkpoint.json
```

### 各目录说明

**GOAL.md**

目标持久化文件。系统在创建工作空间时自动初始化（空文件）。

Agent 在执行协议第 1 步（Intent & Goal Extraction）时填写内容，包括原始需求、具体目标、可验证标准和执行状态。

AgentEnvInjector 在每次请求时读取此文件并注入到系统提示词的 `<current_goal>` 块中，确保多轮对话中目标不丢失。

对于酒馆任务，TaskScheduler 会在分发时预填目标内容，包含「完成后更新酒馆任务状态」的终极目标。

子 Agent 工作空间也有独立的 GOAL.md，可由父 Agent 或系统预填。

**sessions/**

会话持久化目录，存储 LLM SDK 的消息历史。

每个 session 一个子目录，包含 messages.jsonl 文件，记录用户和 Agent 之间的完整对话。

格式为 JSONL，每行一条 AgentInputItem，追加式写入。

主 Agent 的 sessionId 通常等于 threadId。

**contexts/**

LLM 请求上下文快照目录。

每次调用 LLM 时，完整的请求上下文（包括系统提示词、工具定义、消息历史、压缩状态）会保存为一个 JSON 文件。

文件名格式：`YYYY-MM-DDTHH-mm-ss-SSS.json`

用于调试、回溯和分析 LLM 调用。

**events/**

流式事件记录目录。

events.jsonl 文件记录 Agent 执行过程中的所有流式事件，包括思考、工具调用、工具结果、输出等。

格式为 JSONL，每行一个 StreamChunk，追加式写入。

这是 Agent 执行的完整时间线，可用于审计和回放。

**skills/**

Agent 自生成的技能目录。

Agent 在执行过程中可以创建新的 Skill，存储在此目录。

每个 Skill 是一个子目录，必须包含 SKILL.md 文件。

这些 Skill 仅对当前 Agent 可见，优先级高于内置和用户 Skill。

**extensions/**

Agent 自生成的扩展目录。

Agent 可以创建 Extension 来扩展系统能力，存储在此目录。

每个 Extension 是一个子目录，包含 extension.json 和实现文件。

这些 Extension 仅在当前 Agent 运行时加载。

**output/**

Agent 输出文件目录。

Agent 生成的文档、图片、代码等输出文件统一存放在此目录。

**logs/**

Agent 运行日志目录。

记录 Agent 的运行日志，便于调试和问题排查。

**memory/**

Agent 短期记忆目录。

Agent 可以在执行过程中记录笔记、待办事项等信息。

与全局 memory 目录不同，这是 workspace 级别的临时记忆。

**tasks/**

多 Agent 协作任务目录。

当主 Agent 委托任务给子 Agent 时，会在此目录下创建任务子目录。

详见下文的各类子 Agent 模式。

**checkpoint.json**

执行检查点文件。

记录 Agent 的执行状态，包括 threadId、runStatus、更新时间等。

用于断点恢复和状态追踪。

## 子 Agent 模式一：工具委托 delegate

工具委托模式下，主 Agent 将子任务委托给专业 Agent 执行。

### 目录结构

```
{userHome}/workspaces/{threadId}/
└── tasks/
    └── {taskId}/
        ├── agents/
        │   ├── {agentId-1}/
        │   │   ├── sessions/
        │   │   │   └── {threadId}:delegate:{agentId-1}/
        │   │   │       └── messages.jsonl
        │   │   ├── contexts/
        │   │   │   └── 2026-02-21T11-00-00-000.json
        │   │   ├── events/
        │   │   │   └── events.jsonl
        │   │   ├── skills/
        │   │   ├── extensions/
        │   │   ├── output/
        │   │   │   └── analysis.md
        │   │   ├── logs/
        │   │   └── checkpoint.json
        │   │
        │   └── {agentId-2}/
        │       └── (同上)
        │
        ├── results/
        │   ├── {agentId-1}.md
        │   └── {agentId-2}.md
        │
        └── experiences/
            ├── tool-failure-experience.md
            └── solution-pattern.md
```

### 目录说明

**tasks/{taskId}/**

单个任务的根目录。

taskId 可以由 task_plan 工具生成，也可以由 delegate_to_agent 自动生成。

同一 taskId 下的多个子 Agent 可以共享 experiences 和 results。

**tasks/{taskId}/agents/{agentId}/**

单个子 Agent 的完整工作空间。

这是一个独立的 workspace，包含与主 Agent 相同的目录结构。

子 Agent 在此目录下执行，所有文件操作都限制在此范围内。

**tasks/{taskId}/agents/{agentId}/sessions/{threadId}:delegate:{agentId}/**

子 Agent 的会话目录。

sessionId 格式为 `{threadId}:delegate:{agentId}`，确保唯一性和可追溯性。

messages.jsonl 记录主 Agent 与子 Agent 之间的交互。

**tasks/{taskId}/results/**

任务结果汇总目录。

每个子 Agent 执行完成后，会生成一个结果文件 `{agentId}.md`。

包含任务描述、执行时长、工具调用次数、输出内容等。

主 Agent 可以读取这些结果文件来整合子 Agent 的工作成果。

**tasks/{taskId}/experiences/**

任务执行经验目录。

子 Agent 在执行过程中遇到的问题、解决方案、最佳实践等可以写入此目录。

后续委托的子 Agent 会自动获得这些经验作为上下文。

实现经验共享和知识积累。

### 执行流程

用户发起请求 → 主 Agent 分析 → 决定委托 → delegate_to_agent 工具

创建 tasks/{taskId}/ 目录

创建 agents/{agentId}/ 子 workspace

收集 experiences/ 中的已有经验

组装消息（task + context + experiences）

创建子 Agent Builder

手动设置 workspaceRoot 为 agents/{agentId}/

执行子 Agent

结果写入 results/{agentId}.md

返回给主 Agent

## 子 Agent 模式二：统筹者 orchestrator

统筹者模式下，程序先规划任务，然后按计划调度多个 Worker Agent 协作执行。

### 目录结构

```
{userHome}/workspaces/{threadId}/
└── tasks/
    └── {taskId}/
        ├── plan.md
        ├── status.json
        │
        ├── planner/
        │   ├── sessions/
        │   │   └── {threadId}:planner/
        │   │       └── messages.jsonl
        │   ├── contexts/
        │   └── plan-versions/
        │       ├── plan-v1.json
        │       ├── plan-v2.json
        │       └── ...
        │
        ├── workers/
        │   ├── {subtaskId-1}/
        │   │   ├── sessions/
        │   │   │   └── {threadId}:worker:{subtaskId-1}/
        │   │   │       └── messages.jsonl
        │   │   ├── contexts/
        │   │   ├── events/
        │   │   ├── output/
        │   │   ├── status.json
        │   │   └── result.md
        │   │
        │   └── {subtaskId-2}/
        │       └── (同上)
        │
        ├── shared/
        │   ├── context.json
        │   └── messages.jsonl
        │
        └── checkpoints/
            ├── checkpoint-stage-1.json
            └── checkpoint-stage-2.json
```

### 目录说明

**tasks/{taskId}/plan.md**

任务执行计划文件。

Planner Agent 分解任务后生成的执行计划，包含 stages、subtasks、依赖关系等。

Markdown 格式，便于人类阅读。

**tasks/{taskId}/status.json**

任务执行状态文件。

记录当前执行到哪个 stage、哪个 subtask、状态、进度等。

JSON 格式，便于程序解析和更新。

**tasks/{taskId}/planner/**

Planner Agent 的工作目录。

Planner 是一个特殊的 Agent，负责分析用户需求并生成执行计划。

它的 sessionId 格式为 `{threadId}:planner`。

**tasks/{taskId}/planner/plan-versions/**

计划版本目录。

当执行过程中需要重新规划（replan）时，会生成新版本的计划。

每个版本保存为独立的 JSON 文件，便于对比和回溯。

**tasks/{taskId}/workers/{subtaskId}/**

Worker Agent 的工作目录。

每个 subtask 由一个 Worker Agent 执行，拥有独立的工作空间。

Worker 的 sessionId 格式为 `{threadId}:worker:{subtaskId}`。

**tasks/{taskId}/workers/{subtaskId}/status.json**

Worker 执行状态文件。

记录 subtask 的状态、开始时间、完成时间、依赖的其他 subtask、输出等。

**tasks/{taskId}/workers/{subtaskId}/result.md**

Worker 执行结果文件。

Worker 完成后生成的结果报告，供 Orchestrator 聚合和传递给依赖方。

**tasks/{taskId}/shared/**

共享上下文目录。

Orchestrator 和所有 Worker 共享的上下文信息。

context.json 记录全局状态，messages.jsonl 记录 Worker 之间的通信。

**tasks/{taskId}/checkpoints/**

执行检查点目录。

每个 stage 完成后保存检查点，用于失败恢复和断点续传。

### 执行流程

用户发起请求 → OrchestratorRuntime

创建 tasks/{taskId}/ 目录

启动 Planner Agent

Planner 分析任务 → 生成 plan.md 和 status.json

按 stage 顺序执行

对每个 stage 中的 subtask：

创建 workers/{subtaskId}/ 目录

启动 Worker Agent

Worker 执行 → 写 result.md

保存 checkpoint

所有 subtask 完成 → 聚合结果 → 返回主 Agent

## 子 Agent 模式三：蜂群 swarm

蜂群模式下，多个 Agent 通过 Handoff 机制动态协作，没有预先的计划。

### 目录结构

```
{userHome}/workspaces/{threadId}/
└── swarm/
    ├── context.jsonl
    ├── messages.jsonl
    ├── knowledge-base.jsonl
    ├── progress.jsonl
    │
    ├── artifacts/
    │   ├── code-v1.ts
    │   ├── design-draft.md
    │   └── ...
    │
    └── agents/
        ├── triage/
        │   ├── sessions/
        │   │   └── {threadId}:triage/
        │   │       └── messages.jsonl
        │   └── contexts/
        │
        ├── {roleId-1}/
        │   ├── sessions/
        │   │   └── {threadId}:swarm:{roleId-1}/
        │   │       └── messages.jsonl
        │   ├── contexts/
        │   ├── events/
        │   ├── output/
        │   └── checkpoint.json
        │
        └── {roleId-2}/
            └── (同上)
```

### 目录说明

**swarm/context.jsonl**

Swarm 共享上下文日志。

记录所有 Agent 对共享黑板（SwarmContext）的读写操作。

格式为 JSONL，每行一条操作记录（state_set、state_delete、artifact_added 等）。

支持崩溃后重放恢复。

**swarm/messages.jsonl**

Swarm 消息总线日志。

记录 Agent 之间发送的所有消息（请求帮助、通知进度、共享发现等）。

格式为 JSONL，每行一条 SwarmMessage。

**swarm/knowledge-base.jsonl**

Swarm 知识库日志。

记录重要的协作知识，包括讨论总结、决策记录、里程碑、问题追踪等。

格式为 JSONL，每行一条 KnowledgeEntry。

用于构建协作上下文，注入到 Agent 指令中。

**swarm/progress.jsonl**

Swarm 进度笔记日志。

记录 Swarm 整体的执行进度、阶段性成果、待办事项等。

Agent 可以添加进度笔记，供其他 Agent 参考。

**swarm/artifacts/**

Swarm 产物目录。

Agent 生成的中间产物、最终交付物统一存储在此。

产物名称应语义化，包含版本号或时间戳。

**swarm/agents/triage/**

Triage Agent 工作目录。

Triage 是 Swarm 的入口 Agent，负责分析用户请求并路由到合适的专家。

它的 sessionId 格式为 `{threadId}:triage`。

**swarm/agents/{roleId}/**

角色 Agent 工作目录。

每个角色（coder、researcher、reviewer 等）对应一个 Agent 实例。

它们的 sessionId 格式为 `{threadId}:swarm:{roleId}`。

Agent 之间通过 Handoff 机制转移控制权。

### 执行流程

用户发起请求 → SwarmRuntime

创建 swarm/ 目录

初始化 FileSwarmContext、FileMessageBus、KnowledgeBase

启动 Triage Agent

Triage 分析 → Handoff 给专家 Agent

专家 Agent 执行

需要协助 → 发消息给其他 Agent 或 Handoff

写入 artifacts/、更新 context、添加 knowledge

完成后 Handoff 回 Triage 或直接返回

聚合结果 → 返回用户

## SessionId 命名规范

不同类型的 Agent 使用不同的 sessionId 格式，便于识别和追溯。

**主 Agent**

```
sessionId = threadId
例：283469346464145408
```

**Delegate 子 Agent**

```
sessionId = {threadId}:delegate:{agentId}
例：283469346464145408:delegate:business-analyst
```

**Planner Agent**

```
sessionId = {threadId}:planner
例：283469346464145408:planner
```

**Worker Agent**

```
sessionId = {threadId}:worker:{subtaskId}
例：283469346464145408:worker:subtask-backend-setup
```

**Triage Agent**

```
sessionId = {threadId}:triage
例：283469346464145408:triage
```

**Swarm Role Agent**

```
sessionId = {threadId}:swarm:{roleId}
例：283469346464145408:swarm:coder
```

## 文件路径安全性

由于 Windows 文件系统不允许路径中包含冒号，所有包含冒号的 sessionId 在创建文件路径时会自动替换。

**替换规则**

```
: → __
```

**示例**

```
sessionId: 283469346464145408:delegate:business-analyst
文件路径: sessions/283469346464145408__delegate__business-analyst/messages.jsonl
```

## Workspace 创建时机

不同类型的 Agent 的 workspace 创建方式和时机不同。

**主 Agent**

由 AgentEnvInjector.injectEnv() 自动调用 Env.getAgentWorkspaceDir(sessionId) 创建。

在顶层 workspaces/ 目录下创建独立 workspace。

**Delegate 子 Agent**

由 delegate_to_agent 工具手动创建嵌套目录。

调用 fs.mkdirSync() 创建 tasks/{taskId}/agents/{agentId}/ 及其子目录。

手动设置 builder.workspaceRoot()、sessionDir()、contextDir()。

**Orchestrator Worker**

由 WorkerCoordinator 创建 workers/{subtaskId}/ 目录。

手动设置 builder 的各个目录路径。

**Swarm Agent**

由 SwarmRuntime 创建 swarm/agents/{roleId}/ 目录。

手动设置 builder 的各个目录路径。

## 与 Env.getAgentWorkspaceDir 的关系

Env.getAgentWorkspaceDir(id) 的职责是为顶层 Agent 创建 workspace。

它会根据传入的 id 在 workspaces/ 下创建目录，并初始化标准的子目录结构。

**使用场景**

- 主 Agent：传入 threadId，创建顶层 workspace
- 测试环境：传入测试 session ID
- 开发调试：传入任意 ID

**不使用场景**

- 子 Agent：它们的 workspace 由父 Agent 或协调器手动创建
- 嵌套目录：由具体的多 Agent 工具或运行时负责

## AgentEnvInjector 的职责

AgentEnvInjector.injectEnv() 的职责是为 Agent 注入运行时环境。

包括工作空间路径、Skill 搜索路径、执行协议、工具上下文等。

**注入时机**

每次调用 AgentExecutor.execute() 或 stream() 时，在创建 Runtime 之前自动注入。

**注入内容**

调用 Env.getAgentWorkspaceDir() 获取或创建 workspace

扫描 Skills 并注入 Skill 发现提示

注入执行协议

设置 sessionDir、workspaceRoot、contextDir

构建工具执行上下文（沙箱路径、环境变量等）

**设计原则**

如果 builder 已手动设置 workspaceRoot，则 injectEnv 应尊重这个设置，不覆盖。

这样 delegate-to-agent、orchestrator、swarm 手动设置的嵌套 workspace 才能生效。

## 清理策略

由于 Agent 运行会产生大量文件，需要合理的清理策略。

**自动清理**

completed 状态的 thread，超过 30 天自动归档或删除（可配置）

测试产生的 workspace（sessionId 包含 test 关键字），测试结束后清理

临时 task（taskId 包含时间戳且无后续引用），超过 7 天清理

**手动清理**

用户可以在前端删除 thread，同时删除对应的 workspace

清理所有 workspaces：保留最近 N 个，删除其余

**归档策略**

重要的 workspace 可以压缩归档到对象存储或外部磁盘

归档文件命名：`workspace-{threadId}-{timestamp}.tar.gz`

## 目录权限和安全

所有 workspace 目录的权限应严格控制。

**权限设置**

workspace 目录：700（仅所有者可读写执行）

敏感文件（如 checkpoint.json）：600（仅所有者可读写）

输出文件：644（所有者可读写，其他用户只读）

**路径校验**

所有文件操作必须通过 resolveSandboxPath() 校验。

确保路径在 workspaceRoot 内，防止路径穿越攻击。

Symlink 必须指向 workspaceRoot 内的目标。

**敏感信息**

不允许在 workspace 中存储 API Key、密码等敏感信息。

如需存储，使用加密存储或引用 config 中的占位符。

## 向后兼容

已有的 workspace 目录结构会继续工作，不强制迁移。

新创建的 Agent 使用新的目录结构。

旧格式的 sessionId（无冒号）依然支持，创建顶层 workspace。

## 设计约束

一个 threadId 对应一个主 Agent workspace。

主 Agent workspace 位于 workspaces/{threadId}/ 顶层。

所有子 Agent workspace 必须嵌套在主 Agent workspace 下。

子 Agent 不允许创建顶层 workspace。

sessionId 格式必须遵循命名规范，便于识别 Agent 类型。

文件路径中的特殊字符（如冒号）必须替换为安全字符。

所有目录操作必须经过路径安全校验。

## 扩展性设计

未来可能的扩展方向：

**多用户支持**

在 workspaces 上层增加 users/{userId}/ 目录。

每个用户拥有独立的 workspaces 空间。

**分布式存储**

workspace 可以存储在对象存储（S3、OSS）。

通过 workspace ID 分片到不同存储节点。

**实时协作**

多个 Agent 共享同一个 workspace。

通过文件锁或分布式锁协调并发写入。

**版本控制**

workspace 内集成 Git 仓库。

Agent 的每次修改自动提交，便于回溯和对比。

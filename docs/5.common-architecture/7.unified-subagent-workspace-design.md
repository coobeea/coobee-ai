# 统一多 Agent 目录架构：实体与协作解耦

本文档基于 `6.workspace-directory-structure.md` 中定义的多 Agent 模式，提出一种**“实体（Agent）与协作（Task/Swarm）解耦”**的全新目录架构设计。

## 核心设计理念：分离工位与任务板

在早期的设计中，我们将子 Agent 的工作空间嵌套在 `tasks/` 甚至 `swarm/` 目录下（例如：`tasks/{taskId}/agents/{agentId}/`）。这种设计的缺点在于：

1. **目录层级过深**，结构变得非常复杂。
2. **生命周期绑定**，Agent 被死死绑定在单个任务中，难以跨任务复用上下文（记忆和会话）。
3. **不同架构差异巨大**，难以用统一的工具进行监控和管理。

**新的架构范式：**
如同真实世界中的公司一样，我们将**“员工的工位”**（Agent 工作空间）与**“项目的文件夹”**（Task/Swarm 协作区）完全独立开来。

1. **`agents/` 目录（工位区）**：存放 Thread 下所有被唤醒的子 Agent。无论是 Delegate、Worker 还是 Swarm Role，都在这里拥有统一标准的工作空间。
2. **`tasks/` 目录（任务板）**：仅存放任务定义、执行计划、进度状态和交付结果。Agent 来这里读取要求并提交成果。
3. **`swarm/` 目录（黑板区）**：仅存放蜂群模式的广播消息、共享知识和协同产物。

## 顶层目录结构概览

```
workspaces/{threadId}/

│
```

## 1. 统一的子 Agent 工作空间 (`agents/` 层)

所有在当前 Thread 生命周期内被调用的子 Agent，都会在 `agents/` 下分配一个扁平的文件夹。

### 命名规范

为了避免同名冲突且保持可读性，文件夹命名采用 `{type}-{id}` 的格式：

- Delegate: `delegate-{agentId}` (例：`delegate-coder`)
- Orchestrator: `planner` 或 `worker-{subtaskId}` (例：`worker-setup-db`)
- Swarm: `swarm-{roleId}` (例：`swarm-reviewer`)

### 标准化的内部结构

每个子 Agent 内部**绝对统一**，遵循以下结构：

```
agents/{agentName}/
├── sessions/
│   └── {sessionId}/
│       └── messages.jsonl    (完整的会话历史)
├── contexts/                 (LLM 请求快照)
├── events/                   (流式事件记录)
├── output/                   (该 Agent 自己生成的文件)
├── logs/                     (运行日志)
├── checkpoint.json           (统一的状态文件：startedAt, status 等)
│
├── skills/                   (可选：子 Agent 专属技能)
├── extensions/               (可选：子 Agent 专属工具)
└── memory/                   (可选：跨任务保留的短期记忆)
```

**杀手级优势：跨任务记忆复用**
因为 Agent 独立于 Task 存在，当主 Agent 先在 Task A 委托 `delegate-coder`，后在 Task B 再次委托 `delegate-coder` 时，该 Coder Agent 可以在自己的 `sessions/` 和 `memory/` 中保留前一次的上下文，拥有了“连贯的记忆”！

## 2. 统一的任务协作区 (`tasks/` 层)

无论是 `delegate_to_agent` 还是 Orchestrator（统筹者）规划的任务，都在 `tasks/` 目录中管理。它本质上是一个“项目看板”。

### 2.1 Delegate 模式的任务区

Delegate 模式主要用于单层的任务委托，通常由主 Agent 直接创建。

```
tasks/{taskId}/
├── definition.md       (任务的原始要求/描述)
├── status.json         (任务整体执行状态)
│
├── results/            (接收区：子 Agent 提交的工作报告)
│   ├── delegate-coder.md
│   └── delegate-reviewer.md
│
└── experiences/        (沉淀区：任务执行中总结的 Pattern，供下个任务参考)
    └── error-handling-pattern.md
```

**工作流**：主 Agent 创建 Task 目录 -> 在 `agents/` 唤醒相应的子 Agent 并告知 Task ID -> 子 Agent 独立工作，完成后将结果写入 `tasks/{taskId}/results/` -> 主 Agent 读取结果。

### 2.2 Orchestrator（统筹者）模式的任务区

Orchestrator 模式用于复杂的、需要多步骤规划和多个 Worker 协作的任务。它在 Task 目录下增加了规划和协调的上下文。

```
tasks/{taskId}/
├── definition.md       (任务的原始要求/描述)
├── plan.md             (Planner Agent 生成的执行计划，包含多阶段和子任务)
├── status.json         (任务整体执行状态，处于哪个 stage/subtask)
│
├── shared/             (多 Worker 之间共享的上下文)
│   ├── context.json    (全局状态变量)
│   └── messages.jsonl  (Worker 间的通信记录)
│
├── checkpoints/        (任务阶段性检查点)
│   ├── checkpoint-stage-1.json
│   └── checkpoint-stage-2.json
│
└── results/            (接收区：各阶段 Worker 提交的工作报告)
    ├── worker-setup-db.md
    └── worker-build-api.md
```

**工作流**：

1. 主 Agent 唤醒 `agents/planner` 并告知 Task ID。
2. Planner 生成 `plan.md` 和初始的 `status.json`。
3. 协调器（Coordinator）根据 plan，按顺序唤醒 `agents/worker-{id}`。
4. 各个 Worker 通过读取 `tasks/{taskId}/shared/` 了解全局上下文，完成后将结果写入 `results/` 并更新 `status.json`。
5. 每个 stage 完成后保存到 `checkpoints/`。

## 3. 统一的蜂群协作区 (`swarm/` 层)

对于无需显式规划、依靠自组织的 Swarm 架构，使用独立的 `swarm/` 目录作为协调中枢。

```
swarm/
├── context.jsonl          (共享黑板状态变更日志)
├── messages.jsonl         (Agent 间的通信总线日志)
├── knowledge-base.jsonl   (协作知识库、决策记录)
├── progress.jsonl         (整体进度流)
│
└── artifacts/             (共同交付的产物区)
    ├── architecture-v1.md
    └── code-draft.ts
```

**工作流**：在 `agents/` 下的 `swarm-triage`、`swarm-coder` 等并发运行，它们不看 `tasks/`，而是通过读写 `swarm/` 目录下的共享文件来实现 Handoff 和协同。

## 代码实现接口 (WorkspaceManager)

```typescript
interface SubAgentWorkspaceConfig {
  agentName: string; // 格式: 'delegate-coder', 'planner', 'worker-setup-db'
  sessionId: string;
  type: 'delegate' | 'worker' | 'swarm' | 'planner' | 'triage';
  threadWorkspace: string; // 顶层 workspaces/{threadId} 路径
}

class WorkspaceManager {
  /**
   * 初始化/获取统一的子 Agent 工作空间
   */
  static getOrCreateSubAgentWorkspace(config: SubAgentWorkspaceConfig): string {
    const { agentName, threadWorkspace } = config;

    // 统一落在顶层的 agents/ 目录下
    const workspace = join(threadWorkspace, 'agents', agentName);

    if (!existsSync(workspace)) {
      mkdirSync(join(workspace, 'sessions'), { recursive: true });
      mkdirSync(join(workspace, 'contexts'), { recursive: true });
      mkdirSync(join(workspace, 'events'), { recursive: true });
      mkdirSync(join(workspace, 'output'), { recursive: true });
      mkdirSync(join(workspace, 'logs'), { recursive: true });

      const checkpoint = {
        agentId: config.agentName,
        sessionId: config.sessionId,
        status: 'initialized',
        createdAt: new Date().toISOString(),
        metadata: { type: config.type }
      };
      writeFileSync(join(workspace, 'checkpoint.json'), JSON.stringify(checkpoint, null, 2));
    }

    return workspace;
  }
}
```

## 总结

将 **执行实体（Agent 工作空间）** 与 **协作上下文（Task/Swarm 目录）** 分离，是架构上的一次重大飞跃：

1. **彻底解决了目录嵌套过深的问题**，结构变得极其清爽。
2. **极大地提升了前端监控的可行性**，只需遍历 `agents/` 目录即可渲染“团队成员状态面板”。
3. **赋予了子 Agent 独立的生命周期和连贯记忆**，它们不再是用完即抛的脚本，而是 Thread 中长存的虚拟团队成员。

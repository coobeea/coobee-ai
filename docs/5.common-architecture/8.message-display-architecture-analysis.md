# 消息流展示架构分析与重构计划

## 1. 背景

随着项目（coobee-ai）中 Agent 交互模式的复杂化，对话体中承载的内容不再仅仅是简单的文本，而是包含了：思考过程 (Thinking)、工具调用 (Tool Call)、子智能体委托 (Delegate)、人类审批 (HITL)、执行日志 (Run Status) 等丰富的结构化数据。

目前我们将其统一提取到了 `ChatMessages.vue` 中，并且**已明确业务上不再区分 `thread`（任务日志）和 `copilot`（应用管家）模式，全部统一使用一模一样的紧凑展示逻辑**。但随着业务发展，现有的单体组件架构暴露出了一些局限性。本次通过对比 DeepChat 项目的消息展示逻辑，提取优秀的架构设计经验，并制定后续的重构计划。

## 2. 现状分析 (coobee-ai 当前架构)

### 2.1 现有实现方式

- **单体巨石组件**：所有的 UI 渲染逻辑集中在 `ChatMessages.vue` 一个文件内（约 400+ 行）。
- **多层嵌套条件渲染**：
  - 第一层：代码中仍遗留着根据 `mode` 区分模式的逻辑（这部分将在后续完全移除，只保留唯一一种紧凑模式的展示）。
  - 第二层：根据 `msg.role` 区分用户和助手。
  - 第三层：在助手消息中，通过 `v-for` 遍历 `msg.blocks`，再通过一大堆 `v-if="block.type === '...'"` 渲染 text、thinking、tool、delegate 块。
- **状态和样式耦合**：工具调用的颜色区分、折叠逻辑、状态展示等全都在同一个文件中，样式代码（CSS）也被迫集中在这一个文件里。

### 2.2 痛点

- **违反开闭原则 (OCP)**：如果未来我们需要支持图片渲染、代码高亮执行、MCP 交互卡片，就必须不断修改 `ChatMessages.vue`，导致文件无限膨胀。
- **可维护性差**：模板层级太深，寻找特定类型（如 Tool）的渲染逻辑非常困难。
- **遗留的冗余分支**：虽然业务上已决定仅需一种统一的“紧凑模式”展示逻辑，但现存代码中仍包含用于区分 `thread` 和 `copilot` 结构差异的废弃分支模板，导致代码体积庞大且不清晰。

## 3. 竞品架构分析 (DeepChat)

通过阅读 DeepChat 项目的 `/components/message/` 目录，发现其采用了一种**高度模块化和原子化**的组件设计。

### 3.1 核心设计理念：分层与解耦

DeepChat 将消息展示拆分成了清晰的三层结构：

1. **列表层 (List)**:
   - 负责整体消息列表的管理和滚动。
2. **项容器层 (Item)**:
   - `MessageItemUser.vue` 和 `MessageItemAssistant.vue`。
   - 职责单一：只负责绘制头像、用户名、时间、骨架屏/加载状态，以及底部的操作栏（Toolbar，如复制、重试等）。
3. **内容块层 (Block)**:
   - 针对结构化数据，实现了原子化的组件拆分：
     - `MessageBlockContent.vue` (普通文本/Markdown)
     - `MessageBlockThink.vue` (思考过程，自带折叠逻辑)
     - `MessageBlockToolCall.vue` (工具调用，自带参数/响应展示和 Diff 代码对比)
     - `MessageBlockImage.vue`, `MessageBlockSearch.vue`, `MessageBlockPlan.vue` 等。

### 3.2 优秀特性亮点

- **组件各司其职**：例如 `MessageBlockToolCall.vue` 内部封装了计算属性（判断是否成功、动态获取颜色和图标）、展开/折叠状态以及复制功能。外层 `MessageItemAssistant` 完全不需要知道工具是怎么渲染的。
- **易于扩展**：如果需要支持新的 MCP UI 资源，只需新建一个 `MessageBlockMcpUi.vue`，然后在 `MessageItemAssistant.vue` 的 `v-for` 里加一行 `<MessageBlockMcpUi v-else-if="..." />` 即可。
- **复用性极高**：这些 Block 级的组件可以在任何需要展示消息内容的地方单独拿出来用，而不强依赖外层容器。

## 4. 重构计划与演进方向

基于对 DeepChat 的分析，我们的 `coobee-ai` 项目将在**彻底废弃 `mode` 区分、全面采用唯一一种紧凑展示风格**的前提下，对代码架构进行组件化重构。

### Phase 1: 提取独立块组件 (Block Components)

将 `ChatMessages.vue` 中长篇大论的 `v-if` 代码块提取为独立的组件，放置到 `src/renderer/src/components/chat/blocks/` 目录下：

- `BlockText.vue`：负责渲染普通文本流（后续可在这里无缝引入 Markdown 渲染器）。
- `BlockThinking.vue`：封装思考过程及其折叠逻辑。
- `BlockTool.vue`：封装工具调用状态（调用中、等待审批、完成、失败）及其参数/输出展示。
- `BlockDelegate.vue`：封装多智能体委托状态。
- _优势_：将局部逻辑彻底封装在内部。在这一步中，也将彻底清理掉所有与 `mode` 参数相关的冗余判断逻辑。

### Phase 2: 提取容器层 (Item Components)

- `MessageItemUser.vue`：封装用户消息的气泡样式。
- `MessageItemAssistant.vue`：封装助手消息的框架（包含头像、名字、时间，以及内部遍历渲染各个 Block 组件的逻辑）。

### Phase 3: 改造 `ChatMessages.vue` (聚合层)

将 `ChatMessages.vue` 退化为纯粹的**列表容器与组装器**，其主要职责将变为：

1. 维护自动滚动逻辑。
2. 渲染空状态 (`empty slot`)。
3. 遍历 `messages` 数组，根据 `msg.role` 动态分发给 `MessageItemUser` 或 `MessageItemAssistant`。

### 总结

明确了“只保留一种通用的紧凑展示模式”后，我们在重构时可以大刀阔斧地砍掉原有区分 thread 和 copilot 的冗余模板。在此基础上，采用类似 DeepChat 的**Block 分形架构**，将极大地提升系统未来的可维护性和可扩展性，为后续引入更多复杂的交互卡片（MCP UI、自定义可视化 Artifacts）打下坚实的基础。

# Gateway 架构重设计 — 开发计划

> 参考分析文档: [openclaw-vs-coobee-architecture-analysis.md](./openclaw-vs-coobee-architecture-analysis.md)

---

## 一、设计背景与目标

### 1.1 核心问题

当前主进程对外暴露服务的方式存在**边界模糊**的问题：

- `src/main/api/` 同时映射 HTTP + IPC 两个通道——其中 IPC 是内部通道（渲染进程用），HTTP 是外部通道，两种不同职责混在同一模块里
- `src/main/channels/` 通过 WsHub 的 prefix:action 路由提供实时通信，但协议简陋（无请求追踪、无结构化错误）
- `src/main/ai/gateway/` 是一个未实现的骨架
- 没有一个清晰的"主进程如何对外暴露服务"的架构定义

**解决方向**：将"对外暴露"与"对内服务"明确分层——Gateway 负责对外，API 层专注对内 IPC。

### 1.2 设计目标

**Gateway 是主进程与外部世界之间的唯一桥梁。**

所有外部消费者（渲染进程 WS、MCP、CLI、外部工具）都通过 Gateway 与主进程交互。Gateway 提供：

- 结构化 WS RPC 协议（req/res/event，带请求追踪和错误处理）
- HTTP REST 路由（远期，如 OpenAI 兼容 API）
- 实时事件推送（AI 流式输出、Worker 状态等）
- 方法注册机制（约定式发现 + 动态注册，为插件预留）

### 1.3 不在范围内

- **内部 API 层**：`src/main/api/` 保留为 IPC 内部接口，继续用扫描发现机制为渲染进程服务，与 Gateway 独立
- **认证/权限**：当前阶段不实现，预留接口
- **插件系统**：在 Gateway 方法注册机制上预留扩展点，但不实现完整插件加载

## 二、两层服务架构

### 2.1 核心定位

主进程暴露服务分为**两层**，职责明确分离：

| 层          | 位置                | 通道                     | 消费者                                           | 职责                            |
| ----------- | ------------------- | ------------------------ | ------------------------------------------------ | ------------------------------- |
| **Gateway** | `src/main/gateway/` | WS RPC + HTTP REST       | 外部系统（MCP、CLI、外部工具）+ 渲染进程实时数据 | 对外暴露服务（结构化 RPC 协议） |
| **API**     | `src/main/api/`     | IPC + HTTP（双协议并行） | 渲染进程（Electron 用 IPC，网页版用 HTTP）       | 对内提供前后端交互              |

**Gateway**：对外统一入口。Agent 执行、Worker 管理、系统状态等"对外暴露"的能力都通过 Gateway 提供，使用结构化的 WS RPC 协议（带请求追踪、错误码、事件推送）。

**API**：对内应用接口，**保留现有的 IPC + HTTP 双协议机制**。渲染进程通过 IPC（Electron 桌面版）或 HTTP（网页版）调用内部功能。继续使用现有的：

- `loader.ts` → `discoverApiModules()` 扫描发现
- `decorators.ts` → `@Post()`, `@SSE()`, `@Stream()` 装饰器元数据
- `IpcServer` → `ipcMain.handle()` 注册 IPC 通道
- `HttpServer` → Koa router 注册 HTTP 路由

### 2.2 网络层共享方案

Gateway 和 API 层**共享同一个底层 `http.Server`**（同一端口），但各自负责不同的 URL 空间：

```
统一端口 (VITE_SERVER_PORT=8765)
  │
  ├── /api/*          → HttpServer (Koa) 处理    ← 内部 API 层 HTTP 路由
  ├── /v1/*           → Gateway HTTP Router 处理  ← OpenAI 兼容接口等对外 HTTP
  ├── /gateway/*      → Gateway HTTP Router 处理  ← 健康检查、方法发现等
  └── ws://           → 连接升级
       ├── Gateway WS → GatewayServer 处理        ← 结构化 RPC 协议
       └── (旧 WS      → WsHub 处理，过渡期保留)
```

**实现方式**：

1. `HttpServer` 创建底层 `http.Server` + Koa 应用，注册 `/api/*` 路由
2. `GatewayServer` 做两件事：
   - **WS 层**：创建 `WebSocketServer`，挂载到 HttpServer 的 `http.Server`（HTTP Upgrade）
   - **HTTP 层**：创建自己的 Koa Router，挂载到 HttpServer 的 Koa 应用上（作为中间件）

```typescript
// GatewayServer 启动时
const httpServer = HttpServer.getInstance()

// 1. WS 挂载（与当前 WsServer 相同）
this.wss = new WebSocketServer({ server: httpServer.getHttpServer() })

// 2. HTTP 路由挂载（Gateway 自己的路由）
const gatewayRouter = new Router()
gatewayRouter.get('/gateway/health', healthHandler)
gatewayRouter.get('/gateway/methods', methodsHandler)
gatewayRouter.post('/v1/chat/completions', openaiCompatHandler) // 远期
httpServer.getApp().use(gatewayRouter.routes()) // 挂到 Koa 应用上
```

**路由归属清晰分离**：

- `/api/*` → HttpServer 自己注册（API 层专用）
- `/gateway/*`, `/v1/*` → GatewayServer 注册（Gateway 对外 HTTP 端点）
- `ws://` → GatewayServer 管理（Gateway WS RPC）

### 2.4 判断标准：一个功能放 Gateway 还是 API？

| 问题                                         | 放 Gateway               | 放 API                             |
| -------------------------------------------- | ------------------------ | ---------------------------------- |
| 外部工具/MCP 需要调用吗？                    | 是                       | 否                                 |
| 是 Agent 执行/管理相关吗？                   | 是                       | 不一定                             |
| 是 Electron 原生能力吗？（窗口、文件、系统） | 否                       | 是                                 |
| 需要实时推送吗？                             | 是（Gateway events）     | 否（request-response）             |
| 网页版前端需要调用吗？                       | 不一定（看是否对外暴露） | 是（通过 HTTP，与 IPC 同一套 API） |

## 四、核心协议设计

### 4.1 三种消息类型

**客户端 → Gateway（请求）**：

```typescript
interface GatewayRequest {
  type: 'req'
  id: string // 请求唯一 ID（客户端生成）
  method: string // 'namespace.action' 格式，如 'chat.send'
  params?: Record<string, unknown>
}
```

**Gateway → 客户端（响应）**：

```typescript
interface GatewayResponse {
  type: 'res'
  id: string // 对应请求的 ID
  ok: boolean
  payload?: unknown // 成功数据
  error?: { code: number; message: string } // 错误信息
}
```

**Gateway → 客户端（事件推送）**：

```typescript
interface GatewayEvent {
  type: 'event'
  event: string // 'namespace.action' 格式，如 'stream.message'
  payload: unknown
}
```

### 4.2 与当前协议对比

| 维度     | 当前 prefix:action         | 新 RPC 协议                      |
| -------- | -------------------------- | -------------------------------- |
| 请求追踪 | 无 ID，fire-and-forget     | 每个请求有唯一 ID，可 await 响应 |
| 错误处理 | error 类型全局广播         | 精确返回到发起请求的客户端       |
| 方法发现 | 硬编码 type 字符串         | system.methods 返回所有可用方法  |
| 事件订阅 | 隐式 subscribe/unsubscribe | 显式事件模型 + 订阅管理          |

### 4.3 错误码

| 范围 | 含义             | 示例                                       |
| ---- | ---------------- | ------------------------------------------ |
| 1xxx | 协议错误         | 1001 PARSE_ERROR, 1002 INVALID_MESSAGE     |
| 2xxx | 路由错误         | 2001 METHOD_NOT_FOUND, 2002 INVALID_PARAMS |
| 3xxx | 业务错误         | 3001 SESSION_BUSY, 3002 TIMEOUT            |
| 4xxx | 认证权限（预留） | 4001 UNAUTHORIZED                          |

## 五、核心类设计

### 5.1 自动发现机制（与现有模式对齐）

Gateway 遵循项目已有的**扫描发现**模式，在 `scan.ts` 中新增两个扫描函数：

```typescript
// scan.ts 新增

/** 扫描 Gateway 方法组 */
export function scanGatewayMethods(): DiscoveredModule[] {
  const modules = import.meta.glob('@main/gateway/methods/**/*.ts', { eager: true })
  return filterModules(modules)
}

/** 扫描 Gateway 事件桥接 */
export function scanGatewayEventBridges(): DiscoveredModule[] {
  const modules = import.meta.glob('@main/gateway/events/**/*.ts', { eager: true })
  return filterModules(modules)
}
```

**与现有模式的对比：**

| 模块             | 扫描函数                    | glob 模式                       | 导出约定                    | 类型守卫              |
| ---------------- | --------------------------- | ------------------------------- | --------------------------- | --------------------- |
| API              | `discoverApiModules()`      | `../../api/**/*.ts`             | 类 + `@Post`/`@Get` 装饰器  | `getRouteMetadata()`  |
| WsHub            | `scanWsChannels()`          | `@main/channels/**/*Channel.ts` | 对象实现 `WsChannel` 接口   | `isWsChannel()`       |
| Lifecycle        | `scanLifeCycleHooks()`      | `@main/lifecycle/**/*Hook.ts`   | 对象实现 `LifecycleHook`    | 导出字段检查          |
| **Gateway 方法** | `scanGatewayMethods()`      | `@main/gateway/methods/**/*.ts` | 对象实现 `MethodGroup` 接口 | `isMethodGroup()`     |
| **Gateway 事件** | `scanGatewayEventBridges()` | `@main/gateway/events/**/*.ts`  | 函数实现 `EventBridgeInit`  | `isEventBridgeInit()` |

### 5.2 方法组约定（MethodGroup）

```typescript
// protocol/types.ts

/** 单个方法处理函数 */
type MethodHandler = (params: Record<string, unknown>, ctx: MethodContext) => Promise<unknown>

/** 方法上下文（Gateway 注入） */
interface MethodContext {
  clientId: string
  ws: WebSocket
  meta: ClientMeta
  gateway: Gateway // 供 handler 调用 broadcastEvent 等
}

/** 方法组：一个文件导出一组相关方法 */
interface MethodGroup {
  /** 命名空间，如 'chat', 'stream', 'worker' */
  namespace: string
  /** 方法映射，key 为 action 名（不含 namespace 前缀） */
  methods: Record<string, MethodHandler>
  /** 可选：初始化回调（Gateway 注入自身引用时调用） */
  onInit?: (gateway: Gateway) => void
}
```

**示例：methods/chat.ts**

```typescript
// gateway/methods/chat.ts
export const chatMethods: MethodGroup = {
  namespace: 'chat',
  methods: {
    // 客户端请求 method: 'chat.send' → 路由到这里
    send: async (params, ctx) => {
      const { message, sessionId } = params as { message: string; sessionId?: string }
      // ... 调用 AgentExecutor
      return { sessionId: newSessionId }
    },
    // 客户端请求 method: 'chat.abort' → 路由到这里
    abort: async (params, ctx) => {
      const { sessionId } = params as { sessionId: string }
      // ... 终止 Agent
      return { success: true }
    }
  }
}
```

### 5.3 事件桥接约定（EventBridgeInit）

```typescript
// protocol/types.ts

/** 事件桥接初始化函数签名 */
type EventBridgeInit = (gateway: Gateway) => void
```

**示例：events/StreamBridge.ts**

```typescript
// gateway/events/StreamBridge.ts
import { eventBus } from '@main/common/eventbus'

/** 导出初始化函数，Gateway 启动时自动调用 */
export const initStreamBridge: EventBridgeInit = (gateway) => {
  // 内部 EventBus 事件 → 外部 Gateway 事件
  eventBus.on('stream:message', (sessionId, chunk) => {
    gateway.broadcastEventIf('stream.message', { sessionId, chunk }, (meta) =>
      meta.subscribedSessions.has(sessionId)
    )
  })

  eventBus.on('worker:status', (status) => {
    gateway.broadcastEvent('worker.status', status)
  })
}
```

### 5.4 Gateway（核心编排）

```typescript
class Gateway {
  private server: GatewayServer
  private methods = new Map<string, MethodHandler>()

  /**
   * 启动流程（在 ReadyGatewayHook 中调用）
   *
   * 1. 从 HttpServer 获取 http.Server 实例（共享端口）
   * 2. 创建 GatewayServer（WS 挂载到 http.Server）
   * 3. 自动发现并注册方法组（scanGatewayMethods）
   * 4. 自动发现并初始化事件桥接（scanGatewayEventBridges）
   * 5. 开始监听 WS 连接
   */
  start(): void {
    // 获取 HttpServer 实例（与 WsHub 相同的模式）
    const httpServer = HttpServer.getInstance()
    this.server = new GatewayServer({
      httpServer, // 传入整个 HttpServer（获取 http.Server + Koa app）
      onMessage: (ws, data, meta) => this.handleMessage(ws, data, meta)
    })

    this.discoverMethods()
    this.discoverEventBridges()
    this.server.start()
  }

  // ========= 方法发现（类比 WsHub.discoverChannels） =========

  private discoverMethods(): void {
    const modules = scanGatewayMethods()
    for (const { path, module } of modules) {
      for (const [exportName, exportValue] of Object.entries(module)) {
        if (this.isMethodGroup(exportValue)) {
          this.registerMethods(exportValue as MethodGroup)
          log.debug(`[Gateway] 发现方法组: ${exportName} (来自 ${path})`)
        }
      }
    }
    log.info(`[Gateway] 方法发现完成: ${this.methods.size} 个方法`)
  }

  /** 类型守卫：判断导出值是否为 MethodGroup */
  private isMethodGroup(value: unknown): value is MethodGroup {
    if (!value || typeof value !== 'object') return false
    const obj = value as Record<string, unknown>
    return (
      typeof obj.namespace === 'string' && typeof obj.methods === 'object' && obj.methods !== null
    )
  }

  /** 注册方法组 → 展开为 'namespace.action' 格式 */
  registerMethods(group: MethodGroup): void {
    group.onInit?.(this)
    for (const [action, handler] of Object.entries(group.methods)) {
      const fullName = `${group.namespace}.${action}`
      if (this.methods.has(fullName)) {
        log.warn(`[Gateway] 方法名冲突，覆盖已有: ${fullName}`)
      }
      this.methods.set(fullName, handler)
    }
  }

  // ========= 事件桥接发现（类比 WsHub.discoverChannels） =========

  private discoverEventBridges(): void {
    const modules = scanGatewayEventBridges()
    for (const { path, module } of modules) {
      for (const [exportName, exportValue] of Object.entries(module)) {
        if (typeof exportValue === 'function') {
          ;(exportValue as EventBridgeInit)(this)
          log.debug(`[Gateway] 初始化事件桥接: ${exportName} (来自 ${path})`)
        }
      }
    }
  }

  // ========= 消息路由 =========

  private handleMessage(ws, data: string, meta: ClientMeta): void {
    const msg = JSON.parse(data)
    if (msg.type === 'req') {
      this.handleRequest(ws, msg as GatewayRequest, meta)
    } else {
      // 未知类型 → 协议错误
    }
  }

  private async handleRequest(ws, req: GatewayRequest, meta: ClientMeta): void {
    const handler = this.methods.get(req.method)
    if (!handler) {
      this.server.send(ws, {
        type: 'res',
        id: req.id,
        ok: false,
        error: { code: 2001, message: `Method not found: ${req.method}` }
      })
      return
    }
    try {
      const result = await handler(req.params ?? {}, {
        clientId: meta.connectionId,
        ws,
        meta,
        gateway: this
      })
      this.server.send(ws, { type: 'res', id: req.id, ok: true, payload: result })
    } catch (err) {
      // 结构化错误返回
    }
  }

  // ========= 事件广播 API（供方法组和事件桥接调用） =========

  broadcastEvent(event: string, payload: unknown): void
  broadcastEventIf(event: string, payload: unknown, predicate: ClientPredicate): void
}
```

### 5.5 GatewayServer（网络层）

```typescript
class GatewayServer {
  /**
   * 注意：GatewayServer 不创建自己的 http.Server 或 Koa。
   * GatewayServer 负责 Gateway 的全部网络层（WS + HTTP）。
   * 它不创建 http.Server / Koa app，而是挂载到 HttpServer 已有的基础设施上。
   *
   * WS 层：创建 WebSocketServer，attach 到 HttpServer 的 http.Server
   * HTTP 层：创建 Gateway 专属 Koa Router，挂载到 HttpServer 的 Koa 应用上
   */
  private wss: WebSocketServer
  private router: Router // Gateway 专属 HTTP Router
  private clients = new Map<WebSocket, ClientMeta>()

  constructor(options: {
    httpServer: HttpServer // HttpServer 实例（获取 http.Server + Koa app）
    onMessage: MessageHandler // Gateway.handleMessage 回调
  })

  // ========= 生命周期 =========

  start(): void
  // 1. 创建 WebSocketServer，attach 到 httpServer.getHttpServer()
  // 2. 注册 WS 连接事件（connect, message, close, ping/pong 心跳）
  // 3. 创建 Gateway Router，注册内置 HTTP 端点
  // 4. 将 Router 挂载到 httpServer.getApp()

  close(): void

  // ========= WS 通信 =========

  send(ws, payload: GatewayResponse | GatewayEvent): void
  broadcast(payload: GatewayEvent): void
  broadcastIf(payload: GatewayEvent, predicate: ClientPredicate): number
  forEachClient(callback: (ws, meta: ClientMeta) => void): void
  get clientCount(): number

  // ========= HTTP 路由 =========

  /** 获取 Gateway 的 HTTP Router，供方法组注册额外 HTTP 端点 */
  getRouter(): Router

  // 内置 HTTP 端点（start() 时自动注册）：
  // GET  /gateway/health    → { status: 'ok', uptime, clients }
  // GET  /gateway/methods   → 返回所有已注册 RPC 方法列表
  // POST /v1/chat/completions → OpenAI 兼容接口（远期，Phase 4+）
}
```

**GatewayServer 与 HttpServer 的关系：**

```
HttpServer（基础设施层）               GatewayServer（Gateway 网络适配器）
├── 创建 http.Server ──────────────→ 获取 http.Server → 挂载 WebSocketServer
├── 创建 Koa app ──────────────────→ 获取 Koa app → 挂载 Gateway Router
├── 注册 /api/* 路由（API 层）      ├── 注册 /gateway/* 路由
└── 启动监听                        ├── 注册 /v1/* 路由（远期）
                                    └── 管理 WS 连接 + 心跳
```

> **设计原则**：HttpServer 是"基础设施提供者"（http.Server + Koa app）；
> GatewayServer 是"Gateway 网络适配器"（WS + Gateway HTTP），两者通过
> `getHttpServer()` 和 `getApp()` 对接，共享同一端口但各管各的路由空间。
> API 层的 `/api/*` 路由和 Gateway 的 `/gateway/*`、`/v1/*` 路由互不干扰。

## 六、生命周期集成

```
当前启动顺序：
  ReadyApiRegistrationHook (35) → HttpServer + IpcServer + API 路由注册
  ReadyWsHubHook (40)          → WsHub + Channel 扫描

新启动顺序：
  ReadyApiRegistrationHook (35) → HttpServer + IpcServer + /api/* 路由注册（保留不变）
  ReadyGatewayHook (40)         → Gateway.start()
    ├── 获取 HttpServer 实例
    ├── 创建 GatewayServer
    │   ├── WS: WebSocketServer 挂载到 http.Server
    │   └── HTTP: Gateway Router 挂载到 Koa app（/gateway/*, /v1/*）
    ├── 扫描并注册 RPC 方法（scanGatewayMethods）
    ├── 扫描并初始化事件桥接（scanGatewayEventBridges）
    └── 开始监听
  (ReadyWsHubHook → 过渡期保留，Phase 3 删除)
```

> **关键**：`ReadyApiRegistrationHook` 保留，确保 HttpServer 先启动、API 路由先注册。
> `ReadyGatewayHook` 在其之后执行，获取已有的 `http.Server` 实例来挂载 WebSocket。

## 七、前端适配方案

### 7.1 GatewayClient SDK

在 `src/renderer/src/services/` 或 `plugins/` 下实现前端 SDK：

```typescript
class GatewayClient {
  // 连接管理（自动重连、心跳）
  connect(url: string): void
  disconnect(): void

  // RPC 请求（Promise 化，带超时）
  request(method: string, params?: object): Promise<unknown>

  // 事件监听
  onEvent(event: string, handler: Function): void
  offEvent(event: string, handler: Function): void
}
```

### 7.2 迁移路径

**实时通信（WS）迁移到 GatewayClient：**

```
当前                              → 新方式
───────────────────────────────────────────────
wsService.send({                  → await gatewayClient.request(
  type: 'stream:subscribe',            'stream.subscribe',
  sessionId                             { sessionId }
})                                    )

wsService.onPrefix('stream',      → gatewayClient.onEvent(
  handler)                              'stream.message', handler)

wsService.onPrefix('worker',      → gatewayClient.onEvent(
  handler)                              'worker.status', handler)
```

**Agent 对话迁移到 GatewayClient（原 chat API 已迁移到 Gateway methods）：**

```
invokeBackend('/api/chat/         → await gatewayClient.request(
  agent/chat', msg, sid)                'chat.send', { message, sessionId })
```

**内部 API 保持不变：**

```
invokeBackend('/api/xxx/yyy')     → 不变（继续走 IPC / HTTP 双协议）
```

> `invokeBackend()` 和 `src/main/api/` 的双协议机制（IPC + HTTP）**完全保留**。
> 只有 chat/approval 等迁移到 Gateway 的功能才用 `gatewayClient.request()`。
> 其他内部 API 继续通过 `invokeBackend()` 调用。

## 九、关键设计决策记录

| 决策         | 选择                                                   | 原因                                        |
| ------------ | ------------------------------------------------------ | ------------------------------------------- |
| Gateway 位置 | `src/main/gateway/`（顶层）                            | 不只服务 AI，还有 Worker、系统状态等        |
| Gateway 范围 | 吸收 WsHub + Channels 的对外通信职责                   | 统一对外入口，消除职责分散                  |
| 网络层策略   | GatewayServer 管 WS + Gateway HTTP，挂载到 HttpServer  | HttpServer 是基础设施，Gateway 是对外适配器 |
| API 层保留   | `src/main/api/` + HttpServer + IpcServer 完整保留      | 双协议（IPC + HTTP）机制是网页版的必要基础  |
| 协议格式     | 结构化 RPC（req/res/event）                            | 支持请求追踪、结构化错误、方法发现          |
| 方法发现     | `scanGatewayMethods()` 扫描 `gateway/methods/*.ts`     | 与项目现有模式一致（scan.ts）               |
| 事件桥发现   | `scanGatewayEventBridges()` 扫描 `gateway/events/*.ts` | 与项目现有模式一致                          |
| 方法命名     | namespace.action（如 chat.send）                       | 清晰的分组和路由                            |
| 容错策略     | handler 出错返回结构化错误，不 crash                   | 参考 OpenClaw 容错哲学                      |
| Phase 1 策略 | 与旧系统并存，不破坏现有功能                           | 渐进式迁移，降低风险                        |
